## Plan 03.3-01: Survey, Provenance, and Filter Contract

**Summary:** Solid scaffolding plan that creates the THEME-DIRECTIONS.md shell, encodes all filter rules, and populates the 10-15 entry commercial survey. The three-task structure (shell → survey → verify) is logical and well-scoped for a single autonomous wave.

### Strengths
- Verification commands are concrete, testable, and fail-fast — every critical marker has a PowerShell assertion
- Forbidden-file detection via `git status` + pattern exclusion is a strong guardrail
- The survey row field specification (source name, URL, adopt/reject/open, archetype anchor, etc.) is detailed enough that an agent can't produce an empty table
- D-03c expansion path is acknowledged and tracked in the verification log

### Concerns

**MEDIUM — Survey research method unspecified.** Task 2 instructs the agent to "Research and populate" 10-15 commercial examples but provides zero guidance on HOW to research. A fresh agent needs to know: (a) whether to use web fetch tools, (b) which sites to prioritize beyond the user's itch.io exemplars, (c) how to handle paywalled or inaccessible sources. At minimum, the plan should list the `@canonical_refs` URLs from CONTEXT.md as starting points and note that WebFetch is the expected tool.

**MEDIUM — Plan boundary ambiguity with Plan 02.** Task 1 encodes "all filter rules" but Plan 02 Task 1 also populates DNA mapping, and Plan 02 Task 3 does the per-direction filter audit. The distinction between "encode filter rules in the provenance shell" (Plan 01) and "run the actual per-direction filter audit" (Plan 02) is clear in intent, but the agent could over-encode direction-specific filter decisions in Plan 01 that Plan 02 then must unroll. Consider an explicit scope note: "Plan 01 encodes filter rule definitions and the audit table structure; Plan 02 fills in per-direction pass/fail rows."

**LOW — PowerShell regex for survey row counting.** `'^\| .+ \| https?://'` assumes single-line table rows. Multi-line markdown cells (rare in this context) would be missed. Unlikely to matter in practice but worth noting.

**LOW — Access failure handling is in Task 3 (verification log) but should also be in Task 2 (survey population).** The survey population task should explicitly be told "if a source URL is unreachable, mark it with Access Status: Blocked and use an accessible alternative to fill the same evidence role."

### Suggestions
1. Add a `read_first` entry for the canonical ref URLs from CONTEXT.md to Task 2
2. Add explicit WebFetch tool guidance: "Use WebFetch to retrieve source pages; record Access Status as Blocked if the URL returns 403/404/unreachable"
3. Add a scope note in Task 1: "Encode filter rule *definitions* only; per-direction pass/fail rows are filled by Plan 02"

## Plan 03.3-02: Direction Synthesis and Filter Audit

**Summary:** The core synthesis plan. Three tasks — DNA mapping, 5-direction synthesis, per-direction filter audit — in the right dependency order. The verification checks are the most ambitious: 5 unique subclass names, no Boardwalk Sunset, all struct fields present, forbidden-term detection in adopt context.

### Strengths
- The forbidden-term regex (`Adopt.*synthwave`, etc.) is well-designed — it catches the smart failure mode of "we rejected it, but adopt the color"
- Boardwalk Sunset hard-rejection is enforced by string exclusion in verification
- Base-direction non-preselection and universal-axes are verified
- Per-direction struct fields are exhaustive (name, hex, WCAG, personality, flat/raised behavior, mobile notes, DNA, rationale)

### Concerns

**HIGH — WCAG AA contrast verification is a string presence check, not a computed check.** The plan says "Verify WCAG AA contrast for each base/accent pair" but the verification command only checks for the string `WCAG AA` in the document. An agent could write "WCAG AA: PASS" with a contrast ratio of 1.5:1 and the verification would pass. The plan needs either: (a) a PowerShell contrast-computation step that extracts hex values and computes actual luminance ratios, or (b) a manual-review gate noting that WCAG claims require human verification before the user approval checkpoint.

**HIGH — Universal-axes-still-work filter is subjective and unverifiable.** Task 3 requires asserting that each direction's raised-mode behavior and mobile-sizing notes are "sensible." The automated verification can only check for the presence of text strings like `PASS` — it cannot assess whether "raised buttons are darker" is a meaningful raised-mode design. This is the weakest link in the filter audit. Mitigation: add a manual-verification step or quality rubric (e.g., "raised-mode behavior must describe at minimum: button depth method, stroke behavior change, color shift if any").

**MEDIUM — D-06 seeding vs replacing criteria unspecified.** Task 2 says "Seed from D-06 if still useful, but replace or rebalance if the survey supports a better spread." The agent needs criteria for "if still useful" — otherwise it may blindly seed all 5 archetypes from D-06 without validating them against the survey. Add a guard: "For each D-06 archetype, confirm at least one survey example supports that personality before adopting the archetype; if no survey example matches, the archetype is replaced by a survey-validated alternative."

**MEDIUM — Subclass naming convention enforcement is incomplete.** The verification checks that names end in `NeoCadeTheme` and that Boardwalk Sunset is absent, but doesn't reject other forbidden terms (cyber, synth, neon, noir, dark-arcade, etc.) in subclass names. The forbidden-term check is in Task 3 for the document body, not specifically for direction names. Add a dedicated name-format check: `'[A-Z][A-Za-z0-9]+NeoCadeTheme'` minus known-forbidden stems.

**LOW — Contrast-constrained-use fallback unspecified.** Task 2 says "If a pair fails for intended use, adjust the accent or document a constrained-use note and choose a separate text/focus color that passes." This is the right behavior, but the verification doesn't check that constrained-use notes actually explain the limitation. Add a verification: if the base/accent pair is documented as failing WCAG AA, require the constrained-use note field to be non-empty.

### Suggestions
1. Add a WCAG AA luminance calculation as a verification substep: extract hex values from base/accent fields, compute `relative_luminance(r,g,b)` per WCAG 2.1 formula, assert ratio >= 4.5:1 for normal text or >= 3:1 for large text, and flag any direction below threshold
2. Add quality guidelines for raised/mobile behavior descriptions (minimum content: button depth method, stroke change, color shift)
3. Add D-06 seeding validation gate before synthesis
4. Add explicit forbidden-term check on subclass names

# Phase 3.3 Plan Review

## Summary

The three plans are well-sequenced and faithfully cover the phase mandate: Plan 01 builds the document shell + commercial survey, Plan 02 synthesizes the five directions and runs the filter audit, Plan 03 closes SOURCES.md and gates user approval. Mapping to the 11 ROADMAP success criteria and to context decisions D-01..D-16 is largely complete, the no-mockup/no-`.tres` guardrail is enforced via git-status pattern checks in every plan, and the blocking approval checkpoint is correctly placed at the end (autonomous: false on Plan 03 only). The main weaknesses are (a) verification rigor — several greps are easy to satisfy without meeting the substantive intent, (b) brittle PowerShell regexes and presence-only checks that risk both false positives and false negatives, and (c) one tool-name reference that won't resolve in this harness.

## Strengths

- **Correct ordering and dependency graph.** Wave 1 (provenance + survey) → Wave 2 (DNA + 5 directions + per-direction filter audit) → Wave 3 (SOURCES.md + final audit + approval). Matches the natural data flow: you can't synthesize directions before the survey exists; you can't audit before the directions exist; you can't ship to user before all evidence is in place.
- **Forbidden-file enforcement is explicit.** Each plan re-runs `git status --short` and pattern-matches `.tres`, `.gd`, `addons/`, `main.tscn`, `project.godot`, image extensions. This prevents accidental scope creep into Phase 3.4/4 territory and is the single most important guardrail for a research-only phase.
- **D-decision ledger is comprehensive.** Plan 03 Task 2 explicitly enumerates D-01..D-16 in the final audit grep, which makes it hard for an executor to silently skip any context decision.
- **Approval-gate mechanics correctly modeled.** Plan 03 Task 3 is `type="checkpoint:decision" gate="blocking"` with three options (approve/revise/reject-all), the max-2-revision-rounds rule from D-12 is preserved, and approval is text-level only.
- **Boardwalk Sunset hard-rejection is checked structurally.** Plan 02 verification fails if `BoardwalkSunsetNeoCadeTheme` appears as a class name, which catches the most likely accidental carry-forward.
- **Five-direction count is enforced via unique-class regex** rather than just a "count to 5" prose claim — harder to fudge.

## Concerns

### HIGH

- **`request_user_input` is not a real tool in this harness.** Plan 03 Task 3 says: *"Use `request_user_input` if available; otherwise present a plain-text numbered list and wait."* The actual mechanism is `AskUserQuestion`. A fresh agent reading this plan literally will fail to find `request_user_input` and either fabricate a tool call or fall back to the plain-text path — losing the structured-options UX. **Fix:** rename to `AskUserQuestion` (the deferred tool listed in the harness manifest), and link options by `id` (`approve`/`revise`/`reject-all`).

- **Survey-format verification contradicts CONTEXT.md "Agent's Discretion" clause.** CONTEXT.md says: *"Survey artifact format (markdown table vs per-example dossier vs gallery image)"* is the agent's call. Plan 01 Task 2 verification then hard-requires `^\| .+ \| https?://` (markdown table with URL in column 2). If an executor exercises the documented discretion and writes per-example dossiers or a different column order, verification fails through no fault of theirs. **Fix:** either remove the discretion clause, or weaken the verifier to "≥10 distinct source URLs anywhere in the survey section."

- **Per-archetype anchor coverage is asserted in prose but never machine-checked.** D-08 requires *"at least one example per seeded archetype (D-06)"*. Plan 01 Task 3's verifier only greps for the literal string `personality anchor` — it does not confirm that each of the 5 anchor categories (dark-saturated-arcade, modern-minimal-dark, playful-bubbly, friendly-daylight, expressive-statement) has a corresponding survey row. An executor could legitimately produce 10 rows all clustering on "modern-minimal-dark" and pass the gate. **Fix:** add a per-anchor presence check (e.g., grep for each archetype label in the Personality archetype anchor column).

- **WCAG AA contrast verification is presence-only, not arithmetic.** Plan 02 Task 2 verifies that the literal string `WCAG AA` appears in the doc. It does not validate that any contrast ratio is computed, that the ratio is ≥ 4.5:1 for body text or ≥ 3:1 for large/UI, or that the pair-by-pair audit covers all 5 directions. An executor could write "WCAG AA: not yet computed" and pass. **Fix:** require each direction to include a numeric ratio (regex like `\d+\.\d+\s*:\s*1` per direction) plus a pass/fail label, or run a small contrast computation script as part of verification.

### MEDIUM

- **Plan 02 Task 3 forbidden-term audit produces false positives.** The check `(?i)Adopt.*synthwave` runs as a single-line `-match` against the whole doc. PS `-match` on a multiline string treats the string as one — `Adopt` early in the doc and `synthwave` later in an explicitly-rejected list will appear as a "violation" even when the doc correctly rejects synthwave. Conversely, multiline mode isn't enabled, so cross-line patterns behave unexpectedly. **Fix:** use `Select-String -Pattern` line-by-line, scope to lines under "Adopt" subheadings, or invert the check to scan rejection sections for confirmation language.

- **Survey URL row count uses any markdown row with a URL.** Plan 01 Task 2's row-counting regex `^\| .+ \| https?://` matches any table row whose column 2 is a URL. If the doc has other tables (Provenance, Citation Contract examples, etc.) with URL columns, they inflate the count and a thin survey passes. **Fix:** scope the regex to lines between `## Commercial Example Survey` and the next `## ` heading.

- **`SC-01..SC-11` labels are invented by Plan 03.** ROADMAP.md does not number the success criteria as `SC-01`..`SC-11` — they are an unnumbered list. Plan 03 Task 2 verifies presence of these labels in the final audit log. An executor doing the right substantive audit but using "Success Criterion 1" instead of `SC-01` would fail. **Fix:** either codify the SC-NN labels in the ROADMAP first, or weaken the verifier to count 11 audited criteria without dictating the label format.

- **`base direction deferred` literal-string check is brittle.** Plan 03 Task 2 requires the exact phrase `base direction deferred`. Reasonable phrasings like "base direction selection deferred to Phase 3.4" or "no base preselection" would fail. **Fix:** weaken to a regex like `(?i)base.{0,30}direction.{0,30}deferred|no\s+base.{0,30}preselection`.

- **Direction-count regex over-counts on accidental class-name mentions.** `\b[A-Z][A-Za-z0-9]+NeoCadeTheme\b | Sort-Object -Unique` enforces *exactly 5* unique names. If the doc legitimately references `NeoCadeTheme` superclass behavior using an example like `OrbitalPlaydeckNeoCadeTheme` (the v0 name) in the DNA mapping table — even just to say "do NOT carry forward" — it would push the count to 6 and fail. The Boardwalk Sunset check is also a literal-string check that fires on any mention. **Fix:** restrict the unique-name count to lines under the `## Candidate Directions` section only.

- **CONTEXT.md inconsistency carried into plans.** CONTEXT.md says both "1-3 revision rounds permitted" (in scope bullet) and "max 2 revision rounds" (in D-12). Plans use "max 2." This is the right pick but worth flagging — and the plans should explicitly note they're using the D-12 number, not the scope-bullet number, so a future reader doesn't get whiplash.

### LOW

- **PowerShell `-match` with single-quoted complex regexes works but is fragile.** Patterns like `'(\\.tres$|\\.gd$|^.. addons/|^.. main\\.tscn$|...)'` rely on PowerShell single-quote literal semantics + Select-String regex parsing. They will work, but a small typo (e.g., dropping a backslash) silently weakens the check. Consider extracting these patterns into a `$forbiddenPatterns` array for clarity.
- **No verification that the v0 DNA mapping table has all 5 v0 directions before synthesis.** Plan 02 Task 1 verifies presence of the 5 v0 names, which is good. But Task 2 doesn't gate synthesis on Task 1 having the table populated meaningfully — it just runs in sequence. Low risk because Task 1 must complete first, but worth a cross-check.
- **Plan 03 Task 1 uses "append or insert" for SOURCES.md Section 14.** The instruction is fine, but if an existing Section 14 from another phase exists, "append or insert" leaves room for ambiguity. Suggest: read SOURCES.md and check the highest existing section number before writing — or explicitly say "after the highest existing `## NN.` section."
- **`autonomous: true` on Plans 01 and 02** is correct (they're research-only and have no decision gates), but worth noting that Plan 02 Task 2 includes a meaningful design judgment (replace seeded archetypes if survey supports a better spread). A purely autonomous executor may default to seeded archetypes rather than do the judgment work. Consider adding a "if you replace any archetype, document the replacement reason in the verification log" rule.

## Suggestions

1. **Replace `request_user_input` with `AskUserQuestion`** in Plan 03 Task 3 and add the option-id schema (`approve`, `revise`, `reject-all`) so structured options actually work.
2. **Scope the row-count and class-name regexes to the relevant document sections** (between specific `## ` headings) instead of whole-document matches.
3. **Add per-archetype-anchor presence checks** to Plan 01's verifier so D-08's "≥1 example per archetype" is machine-enforced.
4. **Add numeric WCAG contrast verification** (regex for `\d+(\.\d+)?\s*:\s*1` per direction or, better, a small inline computation step that fails if any pair < 4.5:1 for body text).
5. **Resolve the survey-format discretion contradiction** — either remove the discretion clause from CONTEXT.md or weaken the table-format requirement.
6. **Codify `SC-01..SC-11` labels in ROADMAP.md** before Plan 03 runs, or use a structural count instead of label-string match.
7. **Guard against legitimate v0-name mentions in DNA section** by scoping the 5-class-name uniqueness check to `## Candidate Directions` only, and using a context-aware Boardwalk Sunset check that allows it inside "rejected" prose but not as a class-name declaration.
8. **Replace single-line `-match` patterns** with `Select-String` line-by-line to avoid spurious whole-document matches.
9. **Add an explicit `-NoProfile` consistency check** for the PowerShell verifiers (already present in most, but verify all three plans use it; cold-start PS profiles can break commands).

## Risk Assessment

**MEDIUM.** The plan structure, ordering, and substantive coverage are sound — a competent executor will produce the right artifact. The risks are:

1. **Verification false-pass risk (HIGH within MEDIUM):** several gates are presence-only greps that would let a thin or non-compliant artifact through (`WCAG AA` literal, `personality anchor` literal, single-substring archetype anchor checks). This is the main concern: passing the gate ≠ meeting the criterion.
2. **Tool-name mismatch (`request_user_input`)** is a real but easily-fixed bug that will surface at the approval gate — the highest-stakes moment of the phase.
3. **Verification false-fail risk (MEDIUM):** the over-strict regex patterns (markdown table format, `SC-NN` labels, `base direction deferred` literal) could block correct work and force unnecessary revision cycles.

None of these risks endanger forbidden-file boundaries or the no-mockup/no-`.tres` guardrails — those checks are robust. The risks are confined to the quality of the research artifact and UX at the approval gate. Addressing the 4 HIGH-severity concerns above would drop overall risk to LOW.
