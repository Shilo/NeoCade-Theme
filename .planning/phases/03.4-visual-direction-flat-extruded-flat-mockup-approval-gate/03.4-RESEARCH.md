# Phase 3.4 Research: Visual Direction Mockup + Approval Gate

**Phase:** 03.4-visual-direction-flat-extruded-flat-mockup-approval-gate  
**Created:** 2026-05-06  
**Purpose:** Summarize what planning must know before creating Phase 3.4 execution plans. This phase does not need fresh source discovery; it composes the completed Phase 3.1, 3.2, and 3.3 research into a mockup workflow.

## Research Outcome

Phase 3.4 is ready to plan from existing evidence. No new web or engine research is needed before planning because:

- Phase 3.1 already defines the flat MD3 / MD3 Expressive visual language, Flat-3D construction rules, and raised Control-family matrix.
- Phase 3.2 validates dynamic `NeoCadeTheme` feasibility. Its subclass controls are historical research evidence; production is now the 2026-05-06e/f single concrete class + data-only `.tres` architecture.
- Phase 3.3 already approves the five direction inputs: Pulse, Slate, Bubble, Daybreak, and Burst.
- The updated Phase 3.4 context and Plan 02 closeout resolve the remaining planning ambiguities: 15 Stage 1 boards, representative concept fidelity, Pulse as implementation-priority finalist / recommended starter, formula-driven HTML/CSS dynamic proof, and recommended-starter selection with no architectural privilege.

## Planning Implications

### Mockup Pipeline

The plan should create a reusable HTML/CSS/JS mockup framework under `.planning/mockups/3.4/`. The framework should be data-driven enough that Pulse, Slate, Bubble, Daybreak, and Burst can share component templates while varying palette, shape, accent behavior, raised offset parameters, and density tokens.

Stage 1 is lightweight: 15 concept boards (desktop-flat, mobile-flat, mobile-raised per direction), using representative controls only. Stage 1 is a taste filter, not the full coverage proof.

Finalist work is expensive and exhaustive: Pulse receives the full 4-grid, every required Control, and state-combination proof.

### Required User Gates

The executor must stop for user input at two points:

1. After Stage 1 concept boards: user selects finalists. This is closed; Pulse is selected as recommended starter / implementation priority and all five directions remain v1 variations.
2. After full-fidelity finalist mockups: user approves final themes and confirms exactly one recommended starter direction.

These decisions cannot be auto-resolved.

### Design Token Handoff

`.planning/DESIGN_TOKENS.md` is the final Phase 3.4 handoff to Phase 4. It must be single-class/data-resource-oriented, not a static TokenSet matrix and not a subclass recipe. It must record the recommended starter, approved themes, per-direction export values and Theme Editor override intent, shared `NeoCadeTheme` class contract, flat/raised behavior, desktop/mobile behavior, AUTO notes, and the explicit no-per-direction-`.gd` production rule.

## Risks to Plan Around

| Risk | Planning response |
|---|---|
| Concept boards become too expensive | Keep Stage 1 to representative controls only. |
| Full-fidelity mockups silently omit Controls or states | Build a generated coverage matrix and checklist into the finalist plan. |
| Direction selection happens before the user sees raised variants | Stage 1 must show flat and raised for all five directions. |
| Planner treats Pulse as an architectural base | Recommended starter is a UX/documentation default only; `NeoCadeTheme` class defaults do not become Pulse. |
| HTML mockups drift from dynamic Godot architecture | Use data/formula-driven CSS that mirrors `base_color`, `accent_color`, `raised`, and `platform`. |
| Production implementation leaks into mockup phase | Phase 3.4 may write planning/mockup/design-token files only; no `addons/neocade_theme/` styling changes. |
