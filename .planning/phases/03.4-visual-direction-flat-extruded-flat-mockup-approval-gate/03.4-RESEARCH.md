# Phase 3.4 Research: Visual Direction Mockup + Approval Gate

**Phase:** 03.4-visual-direction-flat-extruded-flat-mockup-approval-gate  
**Created:** 2026-05-06  
**Purpose:** Summarize what planning must know before creating Phase 3.4 execution plans. This phase does not need fresh source discovery; it composes the completed Phase 3.1, 3.2, and 3.3 research into a mockup workflow.

## Research Outcome

Phase 3.4 is ready to plan from existing evidence. No new web or engine research is needed before planning because:

- Phase 3.1 already defines the flat MD3 / MD3 Expressive visual language, Flat-3D construction rules, and raised Control-family matrix.
- Phase 3.2 already validates the dynamic `NeoCadeTheme` architecture and documents the super-first subclass contract.
- Phase 3.3 already approves the five direction inputs: Pulse, Slate, Bubble, Daybreak, and Burst.
- The updated Phase 3.4 context already resolves the remaining planning ambiguities: 10 Stage 1 boards, representative concept fidelity, 1-3 finalist funnel, formula-driven HTML/CSS dynamic proof, and delayed base-direction selection.

## Planning Implications

### Mockup Pipeline

The plan should create a reusable HTML/CSS/JS mockup framework under `.planning/mockups/3.4/`. The framework should be data-driven enough that Pulse, Slate, Bubble, Daybreak, and Burst can share component templates while varying palette, shape, accent behavior, raised offset parameters, and density tokens.

Stage 1 should be lightweight: ten concept boards, one flat and one raised per direction, using representative controls only. Stage 1 is a taste filter, not the full coverage proof.

Finalist work should be expensive and exhaustive: only 1-3 user-selected finalists get the full 4-grid, every required Control, and state-combination proof.

### Required User Gates

The executor must stop for user input at two points:

1. After Stage 1 concept boards: user selects 1-3 finalists.
2. After full-fidelity finalist mockups: user approves N final themes and chooses exactly one `NeoCadeTheme` base direction.

These decisions cannot be auto-resolved.

### Design Token Handoff

`.planning/DESIGN_TOKENS.md` is the final Phase 3.4 handoff to Phase 4. It must be subclass-recipe-oriented, not a static TokenSet matrix. It must record the base direction, approved themes, per-direction defaults and deltas, shared superclass contract, flat/raised behavior, desktop/mobile behavior, and the mandatory `super._regenerate()` first rule.

## Risks to Plan Around

| Risk | Planning response |
|---|---|
| Concept boards become too expensive | Keep Stage 1 to representative controls only. |
| Full-fidelity mockups silently omit Controls or states | Build a generated coverage matrix and checklist into the finalist plan. |
| Direction selection happens before the user sees raised variants | Stage 1 must show flat and raised for all five directions. |
| Planner preselects a base direction | Base selection is deferred to the final user gate only. |
| HTML mockups drift from dynamic Godot architecture | Use data/formula-driven CSS that mirrors `base_color`, `accent_color`, `raised`, and `platform`. |
| Production implementation leaks into mockup phase | Phase 3.4 may write planning/mockup/design-token files only; no `addons/neocade_theme/` styling changes. |

## Recommended Plan Breakdown

1. Mockup foundation and formula data contract.
2. Stage 1 concept boards and finalist-selection checkpoint.
3. Finalist full-fidelity 4-grid mockups and final approval checkpoint.
4. `DESIGN_TOKENS.md`, closeout audits, and Phase 4 handoff.
