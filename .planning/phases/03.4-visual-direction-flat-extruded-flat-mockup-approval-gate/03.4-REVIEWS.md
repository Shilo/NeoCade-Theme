## OpenCode Review

### Summary

The four plans form a coherent, well-gated pipeline: foundation -> concept boards -> finalist 4-grid -> design tokens + closeout. Dependency ordering is correct, user decision gates are placed at the right checkpoints, and every plan enforces the "no production addon/theme file changes" boundary. All Phase 3.4 requirements are traceable to specific plans, and the 27 context decisions are addressed through plan must-haves and task acceptance criteria.

### Strengths

- Clean separation of auto and user-gated work. Plans 01 and 04 are autonomous, while Plans 02 and 03 have blocking decision checkpoints at the exact points where user taste judgment is required.
- Forbidden-surface enforcement is thorough. Every plan includes `git status` checks that fail if `addons/`, `main.tscn`, `project.godot`, `.tres`, or `.gd` files change.
- Anti-cyberpunk and anti-texture filters are operationalized through render-check updates and forbidden visual-treatment markers.
- Dynamic architecture proof is structural. Plan 01 encodes `base_color`, `accent_color`, `raised`, and `platform`; Plan 03's 4-grid proves one direction across all four export-axis cells.
- Base-direction selection is properly deferred until Plan 03 Task 4, after full-fidelity finalist review.
- Phase 4 handoff is explicit in Plan 04 through `DESIGN_TOKENS.md` sections and the mandatory `super._regenerate()` first rule.

### Concerns

#### HIGH

None.

#### MEDIUM

- M-1: Mobile mockup dimensions are underspecified. Plans reference `platform=MOBILE` and D-23/D-24, but no plan defines the mobile viewport width or tap-target pixel values to use in HTML mockups. The executor should at minimum document the chosen viewport size in `render-check.md`.
- M-2: Plan 03 Task 2 Control/state coverage verification is structural but not combinatorial. It checks that Control names and required state markers appear somewhere, not that each applicable Control/state is actually rendered. The coverage matrix artifact is the intended manual verification layer and should be built thoroughly.
- M-3: The 35 vs 37 Control count discrepancy persists in downstream references, while Plan 03 lists more names because it includes split scrollbar axes and container/editor-adjacent entries. The coverage matrix should use `MINIMAL-THEME-COVERAGE-DELTA.md` as the canonical source and annotate composite rows.

#### LOW

- L-1: Screenshot rendering has a manual fallback with no quality floor. The executor should attempt Playwright first and record exact browser/OS/viewport details if manual capture is needed.
- L-2: Plan 02 Task 1 concept-board direction-count verification uses loose string matching. This is acceptable as a fast sanity check because user visual review is the real verification.
- L-3: Plan 04 closeout audit markers assume specific abbreviation formats and do not validate content depth. This is acceptable for Phase 3.4 closeout because approval is visual and later phases own final production verification.

### Suggestions

- Add a mobile viewport constant to Plan 01's shell.
- Make the coverage matrix a structured artifact so later phases can audit against it.
- Add a quick sanity check that concept boards render at near-identical dimensions.
- Document Playwright/Edge availability and fallback render path in the Plan 01 README.

### Risk Assessment

Overall risk: LOW. The primary risks, including auto-approval, production leaks, and architecture drift, are structurally blocked by checkpoint types and verification commands. Remaining risks are tooling or execution-quality issues that should not cause Phase 3.4 to fail its goal.

## Claude Review

### Summary

The four-plan breakdown for Phase 3.4 is well-structured, dependency-correct, and faithful to the phase context. Wave ordering maps cleanly to the two mandatory user gates. Hard constraints, including no production `.tres` writes, historical v0 preservation, super-first subclass rule, and anti-cyberpunk/anti-texture filters, are repeatedly audited. Base-direction designation is correctly deferred to the post-finalist gate. Inputs from Phase 3.1, 3.2, and 3.3 are treated as locked rather than re-litigated. No HIGH-severity concerns surfaced.

### Strengths

- Decision discipline: D-01 through D-27 are mechanically traceable into plan must-haves, task acceptance, and closeout audit.
- Two blocking checkpoints are properly modeled: Plan 02 Task 3 for finalist selection and Plan 03 Task 4 for final approval plus base direction.
- Forbidden-surface audits appear throughout and make the hard phase boundary structurally enforceable.
- Forbidden-direction guard prevents rejected or forbidden naming from returning through direction data.
- Single-theme edge case is handled in Plan 04 Task 2.
- Pitfall 1.1 state combinations are explicitly listed in Plan 03 Task 2.
- No production scope creep: Phase 3.4 stays mockup/design-contract only.

### Concerns

#### HIGH

None.

#### MEDIUM

- M1: Coverage matrix verification is marker-only. An executor could satisfy the grep with a sparse legend instead of rendering each Control/state combination. A stronger artifact would enumerate each Control with visible file/anchor evidence.
- M2: Mobile claims lack numeric verification. Plan 03 checks for words like `mobile` and `tap`, but no check forces concrete values such as 48px tap targets or 16px body text. Phase 8 owns the spec, but Phase 3.4 should still surface concrete mockup numbers.
- M3: WCAG AA for text-on-surface is not surfaced in `DESIGN_TOKENS.md` verification. Adding `WCAG`, `contrast`, and `4.5:1` markers would force explicit token-contract documentation.
- M4: The three-revision-round cap is mentioned but not mechanically tracked. A simple `revisions.log` under `.planning/mockups/3.4/` would make D-26 auditable.
- M5: Color-override preview verification is binary. D-14 calls for plausible override examples; verification should enforce at least two distinct override variants per finalist.
- M6: Render evidence is not file-verified. If Playwright is unavailable, no persistent screenshots may exist. The executor should either track screenshots under `.planning/mockups/3.4/` or explicitly record that browser-open review is acceptable.

#### LOW

- L1: Plan 02 finalist count verification can pass if a direction name appears twice in one place rather than distinct flat/raised board containers.
- L2: Filename allowlist for generated screenshots is not explicit. Plan 01's image forbid pattern could block legitimate tracked screenshots if they exist during that plan.
- L3: `TOKEN-NEW-01..10` IDs are roadmap-level IDs but not defined in `REQUIREMENTS.md`, which still uses `TOKEN-01..10`. This is not a planning blocker.
- L4: Plan 02 lacks an explicit "reject all" path. D-26 escalation can cover it if needed.
- L5: The AskUserQuestion mechanism is implicit in checkpoints. This is acceptable for the GSD workflow but should be handled carefully during execution.

### Suggestions

- Add a `coverage-matrix.md` artifact requirement with visible anchors per Control and finalist.
- Add concrete mobile sizing markers such as `48px`, `44pt`, and `16px` to render-check audits, or make a small mobile-spec artifact explicit.
- Extend Plan 04 Task 2 markers with `WCAG`, `contrast`, and `4.5:1`.
- Introduce `.planning/mockups/3.4/revisions.log` for Stage 1 and finalist revision rounds.
- Require at least two distinct override entries per finalist.
- Relax Plan 01's image forbid pattern to exclude `.planning/mockups/3.4/` if screenshot artifacts are tracked.

### Risk Assessment

- Goal achievement: HIGH likelihood. Plans cover all Phase 3.4 roadmap success criteria.
- Hard-constraint violation: LOW. Production `.tres` and implementation edits are repeatedly audited.
- User-gate skip: LOW. Both gates write artifact files and refuse auto-resolution.
- Coverage gap entering Phase 4: MEDIUM. Marker-based verification could pass with sparse mockups, mitigated by visual review and later implementation phases.
- Mobile-spec drift: MEDIUM. No numeric checks at mockup level; Phase 8 must catch final values.
- Historical v0 preservation: LOW. Audits explicitly preserve historical outputs.
