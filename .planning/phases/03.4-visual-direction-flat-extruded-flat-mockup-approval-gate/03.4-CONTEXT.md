# Phase 3.4: Visual Direction Mockup + Approval Gate (Flat / Extruded-Flat) - Context

**Gathered:** 2026-05-06 (updated from 2026-05-04 auto-draft after Phase 3.1, 3.2, and 3.3 completed)
**Status:** Ready for planning. User confirmed all Phase 3.4 discussion recommendations on 2026-05-06.

<domain>
## Phase Boundary

Mock up the five user-approved directions from Phase 3.3 - **Pulse**, **Slate**, **Bubble**, **Daybreak**, and **Burst** - in the flat MD3 / MD3 Expressive + optional extruded-flat idiom. This phase is the hard visual approval gate before Phase 4 implements any production `.tres` styling.

The phase must prove the dynamic `NeoCadeTheme` architecture visually, but it must not implement production theme resources. The approved output is a mockup-driven design contract: final theme selection, base-direction designation, and `.planning/DESIGN_TOKENS.md` written as a subclass-recipe-oriented handoff for Phase 4.

**In scope:**
- Ten Stage 1 concept boards: 5 approved directions x 2 variations (`raised=false` flat and `raised=true` extruded-flat).
- Lightweight representative Control slice in concept boards: enough real UI to judge direction personality, state treatment, hierarchy, and raised behavior without building the full matrix for all five directions.
- User selection of 1-3 finalist directions after concept boards.
- Full-fidelity finalist mockups only for selected finalists, including the full flat x raised x desktop x mobile 4-grid.
- Dynamic-system proof in mockups: same direction/subclass concept shown across flat/raised, desktop/mobile, and `base_color` / `accent_color` override examples.
- Final approval gate where the user chooses N final themes (N >= 1) and picks exactly one approved final theme as the `NeoCadeTheme` base direction.
- `.planning/DESIGN_TOKENS.md` finalized as the Phase 4 contract.
- Anti-cyberpunk, anti-texture, accessibility, and state-combination audits before final approval.

**Out of scope:**
- Production `.tres` styling commits.
- Implementing `NeoCadeTheme` or per-direction subclasses.
- Re-deriving, renaming, or replacing the five Phase 3.3 approved theme directions.
- Re-running Phase 3.1, Phase 3.2, or Phase 3.3 research.
- Full Godot showcase scene implementation.
- Real-device export QA.

</domain>

<decisions>
## Implementation Decisions

### Approved Direction Inputs

- **D-01:** Phase 3.4 uses the five Phase 3.3 approved text-level directions as direct inputs: **Pulse**, **Slate**, **Bubble**, **Daybreak**, and **Burst**. Names, base colors, accent colors, personality summaries, target use cases, flat-mode behavior, raised-mode behavior, and mobile-sizing notes come from `.planning/research/THEME-DIRECTIONS.md`.
- **D-02:** Phase 3.4 does not invent replacement directions. If a planner or reviewer believes a direction itself is wrong, the resolution path is a focused Phase 3.3 revision, not silent redesign inside mockups.
- **D-03:** All five directions remain peer candidates until the Phase 3.4 final approval gate. No base direction is preselected before mockups.

### Stage 1 Concept Boards

- **D-04:** Stage 1 produces **10 concept boards**: each of the 5 approved directions shown in both `raised=false` flat mode and `raised=true` extruded-flat mode.
- **D-05:** Stage 1 concept boards use a **representative slice**, not the full Control matrix. They must include enough real Controls to judge the direction: button/action hierarchy, text/input treatment, selection/list surface, at least one popup/dialog sample, focus/hover/pressed/disabled examples, and a small palette/type/radius swatch area.
- **D-06:** Stage 1 concept boards do not need desktop/mobile 4-grid coverage. They should focus on directional taste and raised-vs-flat feel so the user can choose 1-3 finalists without paying full-fidelity cost for all five.
- **D-07:** Stage 1 must still be honest about the dynamic architecture: the flat and raised boards for a direction are two renderings of the same direction, not two separate themes.

### Finalist Funnel

- **D-08:** After Stage 1, the user picks **1-3 finalist directions**.
- **D-09:** Only selected finalists receive full-fidelity mockups. This preserves the hard approval gate while keeping Phase 3.4 from spending full matrix effort on directions the user does not want.
- **D-10:** Full-fidelity finalist mockups demonstrate every required user-facing Control class and required state combinations, including Pitfall 1.1 combinations such as `pressed_focus`, `checked_focus`, and `hover_pressed`.
- **D-11:** If the user wants a non-finalist revived after seeing finalist mockups, treat that as a focused revision/escalation checkpoint before expanding full-fidelity work.

### Dynamic System Proof

- **D-12:** Phase 3.4 mockups use **formula-driven HTML/CSS rendered via Playwright/Edge** as the visual contract. The CSS should mirror the dynamic superclass model: derived surface ramp from `base_color`, role/accent behavior from `accent_color`, raised-mode hard-offset shapes, and desktop/mobile sizing tokens.
- **D-13:** Full-fidelity finalist mockups show the same direction in the 4-grid:
  - `raised=false`, `platform=DESKTOP`
  - `raised=false`, `platform=MOBILE`
  - `raised=true`, `platform=DESKTOP`
  - `raised=true`, `platform=MOBILE`
- **D-14:** Finalist mockups include a small color-override preview row showing plausible consumer overrides of `base_color` and `accent_color`.
- **D-15:** Phase 3.4 must not expand the Godot spike or author production `.gd`/`.tres` implementation. Phase 3.2 already locked dynamic architecture feasibility; Phase 4 owns production implementation.

### Base Direction and Final Approval

- **D-16:** The base direction is chosen **only after** finalist full-fidelity mockups are reviewed. The user picks one of the approved final themes to become the `NeoCadeTheme` default style.
- **D-17:** The chosen base direction's values become the superclass default `@export` values. A consumer instantiating `NeoCadeTheme` directly gets that style.
- **D-18:** Remaining approved final directions become personality subclasses named `{Name}NeoCadeTheme` and ship as one `.tres` each under `addons/neocade_theme/themes/`.
- **D-19:** `.planning/DESIGN_TOKENS.md` records:
  - final approved theme list and which direction is the base;
  - per-direction class name and `.tres` filename stem;
  - default `base_color` and `accent_color`;
  - personality recipe values or deltas: radii, outlines, color formula parameters, state behavior, accent discipline;
  - shared superclass contract: Inter Variable Roman, state-layer model, focus strategy, anti-texture rules, regeneration mechanics;
  - flat/raised and desktop/mobile variation behavior;
  - mandatory subclass override note: subclass `_regenerate()` must call `super._regenerate()` first.

### Variation Mechanics

- **D-20:** Flat variation (`raised=false`) keeps `shadow_size = -1` on every `StyleBoxFlat` in the final Godot implementation contract.
- **D-21:** Raised variation (`raised=true`) uses extruded-flat hard offset shapes only: solid top shape plus darker offset duplicate. No blur, soft drop shadow, glow, bevel gradient, texture, pattern, embossing, or painterly chrome.
- **D-22:** Raised behavior is strongest on buttons and button-like controls, subtle on tabs/chips/lists/range handles, rare on popup/dialog shells, and absent from passive labels/separators.
- **D-23:** Desktop/mobile sizing follows the dynamic `platform` export model. Desktop uses denser desktop constants; mobile uses larger body text and touch targets. Corner radii remain part of brand identity and do not automatically change just because platform changes.
- **D-24:** `platform=AUTO` behavior is documented from Phase 3.2 but does not need visual proof beyond showing desktop and mobile outputs; Phase 10 owns real target/device validation.

### Review and Revision Gates

- **D-25:** Every concept and finalist board must pass anti-cyberpunk and anti-texture review before user selection or approval.
- **D-26:** Maximum targeted revision rounds remain 3 for Phase 3.4. If final approval is not reached by round 3, stop for escalation before continuing.
- **D-27:** Phase 4 cannot begin until the user approval decision and base-direction selection are written in Phase 3.4 outputs.

### Agent's Discretion

- Exact representative Control slice composition for Stage 1, as long as it covers button/action hierarchy, input, selection/list, popup/dialog, and state samples.
- Exact HTML/CSS file structure and Playwright screenshot script shape.
- Exact presentation layout of the concept gallery and finalist gallery.
- Exact order in which Pulse, Slate, Bubble, Daybreak, and Burst appear, as long as the ordering is not used to imply a base-direction recommendation.

</decisions>

<specifics>
## Specific Ideas

- Pulse, Slate, Bubble, Daybreak, and Burst should be presented as peers until the final approval gate.
- Stage 1 must show both flat and raised for every direction because raised can change the perceived personality of a theme.
- Full fidelity belongs only to finalists, so the user can make a taste cut before exhaustive Control/state work.
- The finalist 4-grid is the central proof that one direction can regenerate across flat/raised and desktop/mobile from the same dynamic superclass model.
- Color override previews should be small and clearly secondary; the primary decision is the default direction identity, not a full dynamic-color product.
- The base direction should be a taste call made after seeing polished finalists, not a planner optimization before mockups.

</specifics>
