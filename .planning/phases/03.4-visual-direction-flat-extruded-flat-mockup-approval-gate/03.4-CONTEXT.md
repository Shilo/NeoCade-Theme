## Implementation Decisions (auto-drafted; refine via `/gsd-discuss-phase 3.3` after Phase 3.1 + 3.2)

### Theme Lineup (DERIVED FROM PHASE 3.3 — Theme Direction Research)

- **D-01:** 5 themes are produced as `NeoCadeTheme` subclasses. **Names, base colors, accent colors, and personality summaries are inputs from Phase 3.3's approved `THEME-DIRECTIONS.md`** — Phase 3.4 does not invent these. If a Phase 3.4 reviewer disagrees with a Phase 3.3 direction, the resolution path is to revisit Phase 3.3 (one revision cycle) rather than redefine direction at the mockup level.
- **D-02:** Phase 3.4's job is to take Phase 3.3's 5 approved directions and:
  - Step 1: Produce 5 lighter-weight concept boards (flat MD3 only, no raised yet) — these visualize Phase 3.3's directions
  - Step 2: Mock up 1-3 user-selected finalists in the 4-grid format (flat × raised × desktop × mobile)
  - Step 3: User approves N final themes; produce DESIGN_TOKENS.md
- **D-03:** Theme subclass names use Pascal case ending in `NeoCadeTheme` (e.g., `PopPlazaNeoCadeTheme`). File names use snake case (`pop_plaza_neocade_theme.tres`). Names come from Phase 3.3's approved directions.

### Mockup Architecture (post-architecture-revision)

- **D-04:** **Mockups demonstrate the dynamic superclass.** Per finalist, each mockup renders the SAME theme in 4 export-state configurations side-by-side (a 4-grid):
  - Top-left: `raised=false, platform=DESKTOP`
  - Top-right: `raised=false, platform=MOBILE`
  - Bottom-left: `raised=true, platform=DESKTOP`
  - Bottom-right: `raised=true, platform=MOBILE`
  Plus 1 additional row showing `base_color` / `accent_color` override examples (consumer-customization preview).
- **D-05:** Mockup format: HTML+CSS rendered via Playwright/Edge (carries forward from Phase 3 v0 toolchain). The CSS is structured to mirror what the dynamic superclass would produce (compute surface ramp from base_color via formula; render flat or raised via offset darker shape; size via desktop or mobile token block). The HTML mockups serve as a visual contract for what the GDScript implementation must produce.
- **D-06:** Mockup output directory: `.planning/mockups/3.3/` (do NOT overwrite v0 in `.planning/mockups/concepts/` or `03-direction-boards.*`)

### Variation Mechanics (locked by Phase 3.2 architecture)

- **D-07:** Flat variation (`raised=false`): `shadow_size = -1` on every StyleBoxFlat (Conflict 3 carry-forward).
- **D-08:** Raised variation (`raised=true`): `shadow_color` = derived darker tone via `_get_base_color`-style formula on the surface color, `shadow_offset = Vector2(0, N)` where N ∈ {2, 4, 6} per Control class (smaller for chrome, larger for buttons), `shadow_size = 0` (no blur — pure offset shape per Flat-3D-UI pattern from Phase 3.1).
- **D-09:** Desktop sizes (`platform=DESKTOP`): Button 32px height, body 14px, standard spacing scale. Mobile sizes (`platform=MOBILE`): Button 48px height, body 16px, +50% spacing on space.4+ (per CROSS-PLATFORM.md). Corner radii STAY IDENTICAL across desktop/mobile (brand identity rule).
- **D-10:** `platform=AUTO` resolves at runtime via `OS.has_feature("mobile")` per Phase 3.2 architecture. Mockups demonstrate AUTO by showing both desktop + mobile renderings side-by-side, captioned "AUTO will pick whichever matches the runtime device." `DESKTOP` and `MOBILE` are **forced** sizes (theme uses that platform's sizes regardless of runtime device).

### Gallery + Approval Workflow

- **D-11:** **Step 1 — Concept boards (flat AND raised per theme):** Per the 5 approved directions from Phase 3.3, each direction gets **two concept boards**: a **flat** rendering AND a **raised (extruded-flat)** rendering. So Step 1 produces **5 directions × 2 variations = 10 concept boards.** User reviews both flat + raised per direction and picks 1-3 finalist directions. Reason: every theme supports both flat and raised at runtime via the dynamic superclass; the user must see both to make informed direction-selection decisions (some directions might be more compelling raised, some more compelling flat). Concept boards do NOT need to demonstrate desktop vs mobile sizing yet — that's Step 2.
- **D-12:** **Step 2 — Finalist full-fidelity mockups:** Selected finalists get full-fidelity mockups in the 4-grid format (D-04). Every user-facing Control × every state combination is demonstrated, including Pitfall 1.1's combinations (`pressed_focus`, `checked_focus`, `hover_pressed`).
- **D-13:** **Step 3 — Approval & DESIGN_TOKENS.md:** User approves N final themes (N ≥ 1). DESIGN_TOKENS.md captures:
  - **Per-theme subclass recipe:** class_name, default `base_color`, default `accent_color`, personality overrides (corner radii by Control class, outline widths, surface-ramp formula parameters per stop, accent tint formula parameters)
  - **Shared base contract:** Inter Variable Roman type scale, M3 state-layer model, focus-ring strategy, anti-texture rules
  - **Variation override blocks:** flat (no shadow); raised (shadow color formula + offset values per Control class); desktop sizes; mobile sizes; AUTO detection logic
  - **Token-superclass→subclass mapping:** which fields the superclass owns vs which the subclass overrides
- **D-14:** **Up to 3 targeted revision rounds.** If not approved by round 3, escalation discussion before proceeding.

### Anti-Cyberpunk + Anti-Texture Filter (carries forward + reinforced)

- **D-15:** Every finalist mockup audited against:
  - Phase 2 anti-cyberpunk patterns (no synthwave / neon-noir / dystopian / scanline)
  - Phase 3 redirect anti-texture rules: no textures, no patterns, no embossing, no painterly/leather/wood/grunge, no gradients on chrome
- **D-16:** Audit happens **before finalist selection** AND **before final approval** — two checkpoints.

### Mobile + Cross-Platform

- **D-17:** Mobile mockups at **360×800** (smallest common phone) **+ 768×1024** (small tablet) viewports per CROSS-PLATFORM.md. Tap-target overlay visible (≥48px on every interactive Control). Both viewports demonstrated in the 4-grid mockup format.

## Specific Ideas

- **Mockup grid format** is the single biggest delta vs Phase 3 v0: each finalist shows the SAME subclass in 4 export-state configurations side-by-side, proving the dynamic system works.
- **Themes the user explicitly liked elements of:** Midnight Marquee colors, Cabinet Chrome colors, Prize Pop Plaza personality (raised buttons OK), Orbital Playdeck modern-iOS-dark feel.
- **Theme the user rejected:** Boardwalk Sunset (too warm, leather, painterly).
- **The "extruded flat" raised variation matters most for Prize Pop Plaza-style themes** where bubbly/jelly raised buttons enhance the playful character. Modern-iOS dark themes (Orbital Playdeck) may use raised more subtly.
- **Anti-texture is a hard rule** — no exceptions, even on background panels. Backgrounds are flat solid colors only.
- **MD3 Expressive's increased saturation + personality** is the design language affordance for "colorful + playful + expressive" without textures. Phase 3.1 surfaces specifics.
- **DESIGN_TOKENS.md is now subclass-recipe-oriented**, not TokenSet-block-oriented (per architecture revision 2026-05-04).
