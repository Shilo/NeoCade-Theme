## Background

CONTEXT.md D-12 said the mockups would be "formula-driven HTML/CSS rendered via Playwright/Edge" with "derived surface ramp from `base_color`, role/accent behavior from `accent_color`, raised-mode hard-offset shapes, and desktop/mobile sizing tokens." None of those decisions are wrong; they are insufficient. They name color and platform tokens but do not require shape-language differentiation per direction. Two corrective tracks are in flight:

2. **Shape-language correction (this addendum):** D-28, D-29, and D-30 below.

## D-28: All v1 directions are dark; light themes are excluded from v1

Per PROJECT.md "Out of Scope: Light color mode (v1)" and the Phase 3.3 Revision Round 2/2 retroactive approval, all five v1 directions use dark base colors:

| Direction | Base | Accent | Contrast |
|---|---|---|---|
| Pulse | `#151A2E` | `#8BFF6A` | 13.62:1 |
| Slate | `#111820` | `#8BD3FF` | 10.94:1 |
| Bubble | `#241326` | `#FFB3E6` | 10.74:1 |
| Daybreak | `#0B2420` | `#76F2D1` | 11.96:1 |
| Burst | `#20112E` | `#FFD166` | 12.33:1 |

The "daylight" feel of Daybreak and the "candy-counter" feel of Bubble are now expressed through bright accents on dark surfaces, not light surfaces. Phase 4 implementation must follow these palette values. Light themes plug in as new data `.tres` resources or consumer-authored `NeoCadeTheme` resources in v2 (PROJECT.md Out of Scope).

## D-29: Mockups follow a same-screen comparison contract with per-direction shape-language differentiation

Phase 3.4 Stage 1 mockups (Plan 02) and Finalist 4-grid mockups (Plan 03) share one common screen layout and one common control inventory across all directions. The same controls appear in the same order with the same content in every direction's mockup — this is what makes side-by-side direction comparison honest.

Direction differentiation comes from shape-language tokens, not from layout, control order, or content. Each direction commits to specific values on at least the following ten axes:

1. Corner radius scale (base radius and scale rule)
2. Button anatomy (radius, padding, border weight, primary/ghost contrast strategy)
3. Chip / tab shape (shape and selected-indicator behavior)
4. Brand mark style (mark shape, size, decoration)
5. Density / spacing scale
6. Focus-ring style (thickness, offset, halo)
7. Type-weight / emphasis scale
8. Surface ramp depth (number of stops, contrast spread)
9. State-layer behavior (hover/pressed/disabled magnitudes)
10. Raised offset depth and which controls lift in raised mode

Each axis must vary between directions. Color tokens (`base_color`, `accent_color`, derived surface ramp, state colors) are necessary but not sufficient differentiation.

Authoritative spec: `.planning/mockups/3.4/image-prompts/direction-shape-language-spec.md`. The previous spec (`fixed-control-order-spec.md`) is deprecated — it encoded only the comparison constants and missed the personality axes.

## D-30: Direction mockups must pass a greyscale sufficiency test

A reviewer who cannot see color (e.g., greyscale conversion of the rendered PNGs, or a colorblind reviewer) must still be able to identify each direction by shape-language alone. If greyscale renders of two directions are visually indistinguishable, shape-language differentiation has collapsed and the spec was not followed; the affected directions must be re-rendered with stronger commitments on the ten axes from D-29.

The render-check artifact (`render-check.md`) must include a greyscale sufficiency-test result row per direction in addition to anti-cyberpunk and anti-texture rows.

## D-31: Single concrete class + data-driven `.tres` per direction (godot-minimal-theme pattern)

**Supersedes (in full):** CONTEXT.md D-17 ("The chosen base direction's values become the superclass default `@export` values. A consumer instantiating `NeoCadeTheme` directly gets that style.") and CONTEXT.md D-18 ("Remaining approved final directions become personality subclasses…"). Also supersedes the same-week 2026-05-06b "symmetric concrete superclass + empty-alias subclass" interpretation and the 2026-05-06c "`@abstract` base + 5 concrete subclasses" interpretation.

The architecture has been simplified to match godot-minimal-theme's proven pattern: **one concrete class, N data-only `.tres` files**. No subclass hierarchy, no `@abstract`, no per-direction `.gd` files. Each approved direction is purely data — a `.tres` with different `@export` values on the same `NeoCadeTheme` class.

### The architecture (9 `@export` properties, finalized 2026-05-06f)

```gdscript
# addons/neocade_theme/neocade_theme.gd
@tool
class_name NeoCadeTheme extends Theme

enum Platform { DESKTOP, MOBILE, AUTO }

# Core (4) — what the consumer is expected to tweak
@export var base_color: Color = Color("#111820"):
    set(value):
        base_color = value
        _regenerate_theme()

@export var accent_color: Color = Color("#8BD3FF"):
    set(value):
        accent_color = value
        _regenerate_theme()

@export var raised: bool = false:
    set(value):
        raised = value
        _regenerate_theme()

@export var platform: Platform = Platform.AUTO:
    set(value):
        platform = value
        _regenerate_theme()

# Shape (5) — values that should be consistent across the entire theme
@export_group("Shape")
@export var corner_radius: int = 12:
    set(value): corner_radius = value; _regenerate_theme()
@export var spacing: int = 4:
    set(value): spacing = value; _regenerate_theme()
@export var raised_strength: int = 3:
    set(value): raised_strength = value; _regenerate_theme()
@export var focus_thickness: int = 2:
    set(value): focus_thickness = value; _regenerate_theme()
@export var outline_width: int = 1:
    set(value): outline_width = value; _regenerate_theme()

# Internal — computed at every regeneration. Dark is the project default;
# is_light flags the deviation (semantically clearer than dark_theme since
# dark = expected, light = exception in this project).
var is_light: bool

func _regenerate_theme() -> void:
    is_light = base_color.get_luminance() >= 0.5
    # Ports godot-minimal-theme's _get_base_color formulas + entry-population logic.
    # Conditional formulas use `if is_light` (light variant) vs default-dark behavior.
    # Theme entries are populated from the @export values + base/accent color formulas.
    # Per-Control specifics (e.g., chip pill shape, brand-mark style) are NOT captured
    # by the @export set — they live in the Theme Editor entry overrides authored
    # per .tres. Per architectural decision 2026-05-06f, the @export set is limited
    # to values that should be consistent across the entire theme; per-direction
    # unique mood lives in Theme Editor authoring per .tres.

# Convention: any future paired x/y @export values use Vector2i
# (currently no paired values in the @export set).
```

```
# addons/neocade_theme/slate_neocade_theme.tres
[gd_resource type="NeoCadeTheme" format=3]

[resource]
base_color = Color(0.066, 0.094, 0.125, 1)         ; #111820
accent_color = Color(0.545, 0.827, 1, 1)           ; #8BD3FF
raised = false
platform = 2                                        ; AUTO
corner_radius = 11
spacing = 5
raised_strength = 2
focus_thickness = 2
outline_width = 1
; ... + Theme Editor entry overrides authored per Slate's personality
;     (e.g., Button/styles/normal: StyleBoxFlat with iOS-pill shape,
;      ChipBar variations, brand-mark styling, etc.)
;     Theme Editor overrides survive _regenerate_theme() if Phase 4
;     designs the regenerate to skip flagged-as-overridden entries.
```

What this means:
- ✅ `NeoCadeTheme.new()` works — concrete class.
- ✅ A custom user `.tres` of type `NeoCadeTheme` works — users author their own themes by saving a NeoCadeTheme instance with their own `@export` values.
- ✅ Each shipped `.tres` is just data: same `NeoCadeTheme` class, different `@export` values per direction.
- ✅ Dark/light is auto-detected from `base_color` luminance — no separate `light_mode` toggle.
- ✅ Consumers can tweak any `@export` property in the inspector at design time, OR set them programmatically at runtime. Setters trigger `_regenerate_theme()` automatically.

### Phase 3.4 "base direction" pick is now "recommended starter"

CONTEXT.md D-16/D-17 originally said the Phase 3.4 user pick "becomes NeoCadeTheme's defaults" (so `NeoCadeTheme.new()` would produce the picked direction's style). Under the single-class data-driven model, `NeoCadeTheme.new()` produces a NeoCadeTheme instance with `@export` defaults baked into the `.gd` (which can be any sensible default — they're just placeholders the user is expected to override per direction). The 5 shipped `.tres` files are what carry direction-specific values. The Phase 3.4 user pick is reframed as the **recommended starter**, which has only two roles:

- It is the default theme preloaded in the showcase scene (`main.tscn`) — `preload("res://addons/neocade_theme/{recommended}_neocade_theme.tres")`.
- It is the "try this first" suggestion in the addon README.

It has no architectural privilege — all 5 directions are peer `.tres` files and ship as peers.

### Phase 4 implementation contract (updated for single-class architecture, 2026-05-06e)

Phase 4 (out of scope for Phase 3.4) must:

1. Delete the existing scaffold at `addons/neocade_theme/neocade_theme.tres` (it is the empty Theme scaffold from project init; under the locked architecture no root `.tres` ships).
2. Author `addons/neocade_theme/neocade_theme.gd` as `@tool class_name NeoCadeTheme extends Theme` (concrete, NOT abstract) with **9 `@export` properties total** (finalized 2026-05-06f):
   - **Core (4):** `base_color: Color`, `accent_color: Color`, `raised: bool`, `platform: Platform`
   - **Shape (5, under `@export_group("Shape")`):** `corner_radius: int`, `spacing: int`, `raised_strength: int`, `focus_thickness: int`, `outline_width: int`
   - Setters on every `@export` property that trigger `_regenerate_theme()`
   - `_regenerate_theme()` that computes `var is_light: bool = base_color.get_luminance() >= 0.5` (dark default; `is_light` flags deviation) and populates derived theme entry color/state values from the `@export` values via formulas (port godot-minimal-theme's `_get_base_color` and entry-population logic, replacing `EditorSettings` with `@export` reads). All conditional branches use `if is_light` (light variant) vs default-dark behavior.
   - Convention: any future paired x/y `@export` values use `Vector2i`. The `@export` set is intentionally minimal — limited to values that should be consistent across the entire theme. Per-direction unique mood comes from Theme Editor entry overrides per `.tres`, not from a long list of exports.
3. Save 5 `addons/neocade_theme/{name}_neocade_theme.tres` files at the addon root, each `[gd_resource type="NeoCadeTheme" format=3]` with that direction's `@export` values. Each `.tres` is created in the Godot editor by:
   - Right-click in FileSystem → New Resource → NeoCadeTheme
   - Set `@export` values per the direction's commitment from `.planning/mockups/3.4/data/directions.json`'s `shape_language` block
   - Save as `{name}_neocade_theme.tres`
   - Optionally use Theme Editor panel to override specific entries on top of regenerated entries (these survive `_regenerate_theme()` if Phase 4 designs the regenerate to preserve manual overrides)
4. Update `main.tscn` to preload the recommended starter's named `.tres` (e.g., `slate_neocade_theme.tres` if Slate is the recommended starter) as the project/scene theme.
5. README documents the consumer pattern: "Pick a direction by name: `preload('res://addons/neocade_theme/{name}_neocade_theme.tres')`. Available: pulse, slate, bubble, daybreak, burst. We recommend starting with `{recommended-starter}_neocade_theme.tres` if you don't have a preference. To author your own custom theme: create a new resource of type NeoCadeTheme, set `base_color` / `accent_color` / `raised` / `platform` / shape-language values to taste, save as your own `.tres`."

Phase 3.4 Plan 04 (DESIGN_TOKENS.md closeout) must record the picked recommended starter `R`, list the 5 `.tres` filenames, document the single-class architecture, and translate the Phase 3.4 mockup `directions.json` `shape_language` blocks into concrete `@export` values that Phase 4 will set per direction.
