# Phase 3.2 Planning Research: Godot Dynamic Theme Architecture

**Authored:** 2026-05-06
**Status:** Ready for planning
**Purpose:** Identify what the Phase 3.2 plans must prove before the project commits Phase 4 to the dynamic `NeoCadeTheme extends Theme` architecture.

## Planning Premise

Phase 3.2 is a feasibility-first research/spike phase. The execution plans must not assume the dynamic architecture works. They must prove it with a contained prototype under `.planning/spikes/dynamic-theme/`, then document the recipe or fallback.

The user decisions in `03.2-CONTEXT.md` tighten the ROADMAP success criteria: the old "4 of 5" threshold is no longer enough. The current gate is strict pass: export-driven regeneration, subclass super-first overrides, runtime application, serialization behavior, and platform detection must all pass. Any failure escalates to the user, while the research still recommends one fallback option for approval.

Planning implications from those docs:
- Theme resources expose runtime-safe setters for theme entries (`set_stylebox`, `set_color`, `set_font`, `set_constant`), so the spike must exercise the actual `Theme` API rather than only inspecting docs.
- Exported variables save on resources and can use setters, so the spike must verify saved `.tres` serialization and editor/runtime behavior rather than assuming it.
- `@tool` code runs in editor and may also run in game depending on guards, so the recipe must document editor/runtime divergence and avoid editor-only APIs.
- `OS.has_feature()` and `OS.get_name()` are valid runtime APIs. Docs also mention Web-specific feature tags such as `web_android` and `web_ios`, which are important for the user-requested Godot-only AUTO strategy.
- `StyleBoxFlat.shadow_color` has no effect when `shadow_size` is lower than 1, so raised/extruded treatment remains a Phase 3.2 evidence item if direct hard-offset shadows are considered.

## Plan Decomposition

The phase should be split into six plans:

1. Create research artifact skeletons and a source map so every later finding has a stable destination.
2. Reverse-engineer Godot editor theme flow and port the passivestar formula model into a runtime-safe recipe.
3. Build the prototype-template spike under `.planning/spikes/dynamic-theme/` with superclass, good subclass, bad subclass, `.tres` instances, test scene, and verifier scaffolding.
4. Run strict feasibility validation and record pass/fail evidence for every load-bearing check.
5. Write the final architecture recipe, subclass contract table, AUTO platform strategy, pitfall catalogue, and fallback recommendation.
6. Update `SOURCES.md` Section 13 and run the final anti-pattern, coverage, and no-addon-change audit.

This sequence gives the executor a hard stop point: if Plan 04 fails a strict check, Plan 05 documents and recommends fallback but does not silently lock it.

## Verification Strategy

Plan verification must include:
- Existence checks for `.planning/research/GODOT-DYNAMIC-THEME-RESEARCH.md`.
- Existence checks for spike scripts, resources, test scene, and verifier report under `.planning/spikes/dynamic-theme/`.
- Scripted checks that the coverage-risk subset (`Button`, `OptionButton`, `CheckBox`, `LineEdit`, `Tree`, `PopupMenu`, `Window`, `ScrollBar`) has required entries after regeneration.
- A negative control proving the subclass-without-super pattern leaves gaps.
- Serialization inspection proving the saved `.tres` contract is understood.
- Local `platform=AUTO` check plus a simulated expected-output table for native desktop, native mobile, Web desktop, and Web mobile.
- `Select-String` anti-pattern audit for `EditorInterface`, `EditorSettings`, and `EDSCALE` in the proposed runtime architecture/spike.
- `git status --short` audit that no files under `addons/neocade_theme/`, `showcase/showcase.tscn`, `project.godot`, or production theme `.tres` resources changed.
