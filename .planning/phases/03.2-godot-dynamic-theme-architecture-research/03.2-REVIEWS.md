# Cross-AI Plan Review: Phase 3.2 — Godot Dynamic Theme Architecture Research

**Reviewed:** 2026-05-06
**Reviewer:** DeepSeek V4 Pro (OpenCode)
**Plans reviewed:** 01 (Wave 0), 02-03 (Wave 1), 04 (Wave 2), 05 (Wave 3), 06 (Wave 4)

---

## 1. Summary

The six plans for Phase 3.2 collectively form a defensible, evidence-first feasibility research pipeline that respects the user's explicit concern ("is this even possible?") and the project's strict-gate discipline. The wave decomposition is logical (skeleton → research/spike → validate → synthesize → closeout), the division between "good subclass / bad subclass" provides a clean negative control, and the escalation/fail-fast posture on strict gate failures prevents silent architecture drift. However, the plans hinge on a single-point-of-failure — a working Godot executable to run the spike verifier — and do not adequately define what "evidence" looks like when Godot is unavailable. Additionally, Plan 03 builds the spike without consuming Plan 02's formula-port research, missing an opportunity for cross-feed within Wave 1.

---

## 2. Strengths

- **Strict-gate discipline is unambiguous.** Plan 04 explicitly requires all 6 load-bearing checks to pass (not "4 of 5"), mandates escalation on any FAIL/BLOCKED, and forbids silently downgrading the architecture. This directly addresses the user's feasibility concern.
- **Negative control design is well-conceived.** Plan 03's `BrokenNoSuperSpikeTheme` subclass that intentionally skips `super._regenerate()` creates a concrete, reproducible proof that resource-level Theme inheritance does NOT happen — exactly the override-mechanics validation demanded by D-10.
- **Evidence table pattern is excellent.** The strict feasibility gate, spike evidence table, and expected-output table for AUTO platform detection create structured pass/fail records that a future verifier (`/gsd-verify-work`) can audit mechanically, not subjectively.
- **Research-only boundary is consistently enforced.** Every plan repeats the no-addon-change rule; Plan 06 closes with a `git status --short` audit. This prevents the common research-phase mistake of leaking prototype code into production directories.
- **The subclass contract table (Plan 05)** bridges creative subclass freedom and structural coverage guarantees — hooks first, direct overrides documented, mobile/a11y guardrails explicit, forbidden APIs listed. This is the right abstraction to carry into Phase 4.
- **Serialization inspection is concrete** (Plan 04 Task 2: read actual `.tres` files and check whether regenerated entries are serialized). Much better than assuming Godot behavior from docs.

---

## 3. Concerns

### HIGH

- **H-1: Godot-availability single-point-of-failure.** Plan 04 Task 1 says "Try to run the verifier... Prefer a headless command if supported. If the verifier cannot run because Godot is unavailable, record `BLOCKED`." This means every strict check — export-driven regeneration, subclass coverage, runtime application — gets `BLOCKED` if Godot can't be invoked. The plans provide no fallback validation strategy for this case (static analysis of generated `.tres` files? manual inspection protocol?). Since the entire phase's primary deliverable is feasibility evidence, a `BLOCKED` outcome here cascades to Plan 05 requiring fallback recommendation even if the architecture is technically sound — the spike simply wasn't exercisable.
- **H-2: Plan 03 does not depend on Plan 02's research.** Both are Wave 1, both depend only on Plan 01. But Plan 03 writes spike code (color formulas, `_regenerate()` logic, subclass hooks) while Plan 02 documents the editor theme flow and passivestar formula port. If the executor builds the spike before or without the formula-port research, the spike may use ad-hoc color math that doesn't reflect the adopted formula pattern. This creates a reconciliation burden in Plan 04/05 or, worse, validates the wrong formula. **Recommendation:** Add a soft dependency from Plan 03 to Plan 02, or at minimum add a Plan 03 task that reads Plan 02's completed research doc before finalizing spike code.

### MEDIUM

- **M-1: Coverage-risk subset may not surface the hardest problems.** The 8-Control subset (Button, OptionButton, CheckBox, LineEdit, Tree, PopupMenu, Window, ScrollBar) is well-chosen for known rough spots (popup-as-separate-window, Tree's 16 styleboxes). However, it omits `TabBar`/`TabContainer` (tab drawing is notoriously fragile in dynamic themes), `ColorPicker` (16 bespoke icons), and `MenuBar` (nested theme resolution). If any of these fail at Phase 4/5, it won't have been caught by the spike. This is acknowledged as a prototype-template limitation, but the risk transfer to Phase 4 should be explicitly listed in Plan 04 output.
- **M-2: Verification commands use `Select-String` which is PowerShell-only.** This is acceptable for a Windows-native project, but Plan 06's Task 3 git-audit uses a regex pattern (`'(\.tres$|\.gd$|^.. addons/|...)'`) that may produce false positives on files outside `addons/` that legitimately changed (e.g., `.planning/` files with `.md` extension won't match, but `.planning/spikes/` `.gd` files WILL match and trigger a false forbidden-file alarm). The regex should exclude `.planning/spikes/` paths.
- **M-3: Phase 3.1 (parallel) outputs are assumed but not referenced.** Plans 02 and 05 reference `MD3-RESEARCH.md` and `FLAT-3D-UI-RESEARCH.md` as context, but Phase 3.1 runs in parallel and these files may not exist when Phase 3.2 runs. If Phase 3.1 lags, Phase 3.2's color formula decisions may conflict with the visual design language Phase 3.1 establishes. The plans should include a note that color formula parameters are provisional until Phase 3.1 completes.
- **M-4: AUTO platform detection for Web is speculative.** Plan 04 Task 3 asks for an expected-output table including `web_android`, `web_ios`, `web_windows`, `web_macos`, `web_linuxbsd`, but Godot's Web export feature tags for mobile detection are not consistently documented or tested in the spike. The plan correctly marks this as "expected-output table" (simulated), but the gap between "expected" and "verified" should be more explicitly warned. Phase 10 would be the first real verification.
- **M-5: No performance bounding for regeneration.** Plan 02 mentions in the decisions section that benchmarking is "informational only," and Plan 05 doesn't include a regeneration performance note. If `_regenerate()` creates hundreds of `StyleBoxFlat.new()` and `Theme.set_*()` calls on every export setter change, editor-time UX may degrade (every color picker drag triggers full regeneration). A brief performance observation (even a rough "regenerated X entries in Y ms" note) should be in the spike evidence table.

### LOW

- **L-1: Plan 04 Task 4 says "set overall feasibility to PASS" but the success criteria only enumerate D-10, D-11, D-12, D-16, D-18, D-19, D-21, D-22, D-23, D-24 — missing D-13, D-14, D-15, D-17, D-20.** This is likely just a documentation gap (those D-IDs are covered by other plans), but the success_criteria block should be exhaustive or explicitly note that remaining D-IDs are covered by other plans.
- **L-2: Plan 05 Task 2 verification looks for "JavaScript" in the research doc to confirm the note about deferred JS bridge.** The match may find false positives if "JavaScript" appears in a source citation or unrelated context. A more precise match (e.g., `"JavaScript bridge"` or `"JavaScript bridge is deferred"`) would be safer.
- **L-3: Plan 01's file inventory doesn't include `.planning/spikes/dynamic-theme/` directory creation in Task 1 verification.** The directory must exist before Plan 03 writes files into it. Plan 03 Task 1 creates the directory implicitly via file writes, but an explicit existence check in Plan 01 or a pre-condition in Plan 03 would be cleaner.
- **L-4: Plan numbering disagreement.** The review prompt references D-14 through D-24 but the CONTEXT.md uses D-14 through D-24 with two D-14 entries and two D-15 entries (Output Structure section reused D-14/D-15 instead of D-25/D-26). This is a source document issue, not a plan issue, but the plans inherit the ambiguity. Plan 05's dependency list references D-14/D-15/D-16 which could mean either the spike-depth decisions or the output-structure decisions.

---

## 4. Suggestions

- **Add a "Godot-unavailable" fallback validation protocol to Plan 04.** If `godot --headless` can't run, the executor should perform: (1) static inspection of serialized `.tres` files for export-vs-entry content, (2) manual review of verifier script logic against Godot docs, (3) documentation of what CAN be validated statically vs what MUST wait for Phase 4 when Godot is available. This converts a hard `BLOCKED` into a partial-evidence result with clear deferred items.
- **Add Plan 02 → Plan 03 soft dependency.** Plan 03 should include a task or pre-condition to read Plan 02's completed formula-port section before finalizing the spike's `_regenerate()` logic. Alternatively, promote Plan 02's formula-port task to Wave 0 (alongside Plan 01) so the spike inherits the right color math from the start.
- **Fix Plan 06 Task 3 regex to exclude spike files.** Change `'(\.tres$|\.gd$|^.. addons/|^.. main\.tscn$|^.. project\.godot$|\.png$|\.jpg$|\.webp$|\.svg$)'` to additionally exclude `'.planning/spikes/'` paths, or whitelist `.planning/` changes.
- **List the coverage-risk subset limitations explicitly in VERIFY-RESULTS.md output.** Plan 04 should include a row: "Known omitted Controls (TabBar, ColorPicker, MenuBar, etc.) — deferred risk to Phase 4."
- **Add a rough regeneration performance note to the spike evidence table.** Even a single timing measurement (`Time.get_ticks_msec()` before/after `_regenerate()`) gives Phase 4 a concrete expectation for editor-time behavior.
- **Harmonize D-ID numbering.** The review prompt's CONTEXT.md has duplicate D-14 and D-15 entries. Plans should reference unique D-IDs or use descriptive names (e.g., "D-spike-depth" vs "D-output-structure") to avoid ambiguity.

---

## 5. Risk Assessment

**Overall: MEDIUM**

**Justification:** The plan decomposition is sound, the strict-gate discipline prevents architecture drift, and the negative-control subclass design is the right way to prove the override-mechanics concern. However, the Godot-availability single-point-of-failure (H-1) means the entire feasibility answer could be `BLOCKED` through no fault of the architecture itself — a particularly sharp risk when the phase's PRIMARY deliverable is "prove it works with a code spike." Combined with the Plan 02/03 cross-feed gap (H-2) that could validate the wrong formula, this pushes the overall risk above LOW despite the plans' otherwise strong scaffolding. The medium-severity concerns (coverage subset gaps, regex false positives, Web AUTO speculation) are individually manageable but collectively add moderate execution friction. No security, performance, or scope-creep issues were identified.
