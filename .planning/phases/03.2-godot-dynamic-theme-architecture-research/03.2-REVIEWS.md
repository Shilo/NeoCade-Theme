## 3. Concerns

### HIGH

None. Both cycle 1 HIGHs are resolved.

### MEDIUM

- **M-1: Plan 04 fallback protocol can't validate runtime behavior statically.** While the protocol correctly differentiates between things that can be inspected statically (script structure, serialization) and things that can't (runtime theme application, actual Tree rendering), some checks will genuinely be BLOCKED without Godot - notably "Does the good subclass `.tres` apply regenerated entries to Controls at runtime?" and "Does AUTO platform detection resolve correctly on mobile?" These are documented as BLOCKED rather than silently passed, which is correct, but the user should understand that a Godot-unavailable scenario still leaves the primary deliverable ("prove it works") partially unproven.
- **M-2: The timing hook is qualified as "where practical."** Plan 03 Task 2 says "a tiny timing observation hook around `_regenerate()` using Godot time APIs where practical." The "where practical" hedge could lead the executor to skip it. This is mitigated by Plan 04 Task 4's explicit performance-note instruction, but a more definitive "include or document why skipped" would close the gap.

### LOW

- **L-1: Plan 05 Task 2 verification uses `"JavaScript bridge"` for precise matching** (resolving cycle 1 L-2), but if the research doc refers to it as "JavaScript bridge is deferred" without the word "bridge" immediately adjacent to "JavaScript" in all places, the match may still fail. Low risk; the concept is unique enough to find manually.
- **L-2: Plan 06 Task 3 `git status` check uses `Select-String -Pattern` with regex alternation `(\.tres$|\.gd$|...)` inside PowerShell.** The outer `ForEach-Object` plus `Where-Object` logic is correct, but the multi-line PowerShell verification block relies on exactly one execution environment (Windows PowerShell). If any agent runs these on Linux, the commands will fail. This is acceptable for a Windows-native project.
- **L-3: Plan 03 Task 4 creates `.tscn` and `.gd` files.** The `.tscn` scene file format is Godot-specific; hand-authoring it requires familiarity with the `[node]`, `[resource]`, and `sub_resource` sections. The plan assumes the executor knows this format - a minor risk if the executor is unfamiliar with Godot `.tscn` structure.

---

## 4. Suggestions

- **In Plan 04 Task 1 fallback protocol, add one sentence explicitly noting which checks are genuinely impossible without Godot** (for example, "runtime theme application to Controls" and "mobile AUTO detection at runtime on a mobile device") so the user sees at a glance which BLOCKED checks are unavoidable vs resolvable later.
- **Strengthen Plan 03 Task 2's timing hook language** from "where practical" to "include a basic `Time.get_ticks_msec()` wrap; if Godot `Time` singleton is unavailable at spike level, document why and mark performance OPEN."
- **Consider adding a note in Plan 05** that if the strict gate has any BLOCKED/STATIC-FALLBACK results, the Phase 4 implementation should start with a quick smoke test of those deferred checks before committing to the full architecture - this makes the risk transfer explicit rather than implicit.
