## Phase Boundary

Determine **whether and how** to implement NeoCade as a runtime-safe `@tool extends Theme` superclass + per-theme subclass architecture, where the superclass dynamically regenerates theme entries from `@export` properties (`base_color`, `accent_color`, `raised`, `platform`) and subclasses contribute personality (shape language, outline widths, color tint formulas).

**In scope:**
- Reverse-engineer Godot's editor theme — how `EditorSettings.interface/theme/{base_color,accent_color,contrast,base_spacing,corner_radius}` flow through `EditorThemeManager` (`editor/themes/editor_theme_manager.cpp`) into theme entries

- Validate `@tool extends Theme` works in Godot 4.6 with `@export` property setters that trigger regeneration, and that subclasses can extend the superclass with their own personality overrides while inheriting all `@export` properties + dynamic regeneration logic.
- Document Godot 4.6 `Theme` class API for runtime theme entry manipulation (`set_stylebox()`, `set_color()`, `set_font()`, `set_constant()`, `clear_*` family) — confirm these work at runtime on all 6 export targets (Windows, macOS, Linux, iOS, Android, Web/Browser).

- Anti-pattern audit: confirm no `EditorInterface` / `EditorSettings` / `EDSCALE` references leak into the proposed runtime-safe architecture

## Implementation Decisions (auto-captured from user revision; refine via `/gsd-discuss-phase 3.2` if needed)

### Architecture Goal (the user's stated design)

- **D-01 (Superclass):** `class_name NeoCadeTheme extends Theme` — the universal dynamic theme base class. `@tool` annotated.
- **D-02 (Superclass exports):**
  - `@export var base_color: Color` — dynamic, drives the surface ramp
  - `@export var accent_color: Color` — dynamic, drives primary accent + state colors
  - `@export var raised: bool = false` — toggles flat (no shadow) vs extruded-flat (offset darker shape)
  - `@export var platform: Platform` — enum `{DESKTOP, MOBILE, AUTO}`, default `DESKTOP`. **Semantics:** `DESKTOP` and `MOBILE` are **forced** sizes (theme uses that platform's sizes regardless of runtime device). `AUTO` **dynamically chooses** at runtime based on the device — desktop sizes on Win/Mac/Linux/desktop-Web, mobile sizes on iOS/Android/mobile-Web — via `OS.has_feature("mobile")`. The naming "AUTO" was chosen over "BOTH" to make the auto-detect semantics explicit (per user clarification 2026-05-04).
- **D-03 (Superclass responsibilities):** Universally handles flat/raised, desktop/mobile sizing, base/accent color tinting (the formula side). Implements the `_get_base_color(brightness_offset, saturation_multiplier)`-style derivation logic ported from passivestar's pattern but driven by `@export` props instead of `EditorSettings`. Provides override hooks (virtual methods) for subclasses to inject personality.
- **D-04 (Subclasses):** `class_name {ThemeName}NeoCadeTheme extends NeoCadeTheme` — per-theme subclass focused entirely on personality: corner radii, outline widths, color tint formulas (e.g., subclass tunes `brightness_offset` / `saturation_multiplier` parameters; subclass overrides specific entry values for character).
- **D-05 (Naming convention):**
  - PascalCase class_name: `{DirectionName}NeoCadeTheme` (5 directions, names finalized by Phase 3.3 — may keep, revise, or replace v0 names per fit; only Boardwalk Sunset hard-rejected)
  - snake_case `.tres` filename: `prize_pop_plaza_neocade_theme.tres` etc.
  - Each subclass `.gd` script + paired `.tres` saved instance under `addons/neocade_theme/themes/`

### Feasibility Validation (PRIMARY DELIVERABLE)

- **D-10:** Phase 3.2 produces a working code spike at `.planning/spikes/dynamic-theme/` (NOT under `addons/neocade_theme/` — this is research, not the v1 implementation). The spike validates:
  - `@tool extends Theme` with `@export` props that regenerate entries on change — works at edit time
  - Subclass extends superclass + adds personality overrides — works at edit time
  - Loading a saved subclass `.tres` at runtime applies the regenerated entries to Controls — works at runtime
  - `OS.has_feature("mobile")` runtime detection at theme application — works on the dev's local machine (desktop = false; mobile target validation deferred to Phase 10)
  - Resource serialization saves exports only (small file), not regenerated entries (would bloat) — verifiable via `.tres` file inspection
  - **Override-mechanics validation (CRITICAL — per user 2026-05-04):** Verify Godot's Theme resolution model — Theme resources do NOT auto-inherit entries from a parent class instance at the *resource* level (each Theme instance is standalone). The override pattern works at the *GDScript code level* via `super._regenerate()` populating base entries, then subclass overrides specifics. The spike MUST validate this concretely: a subclass that ONLY overrides Button entries (without calling `super._regenerate()`) leaves all other Controls (CheckBox, LineEdit, Tree, etc.) UNTHEMED at runtime — proving the resource-level non-inheritance. Then validate the correct pattern: subclass `_regenerate()` calls `super._regenerate()` first, then overrides specifics — the resulting instance has ALL entries populated (base + overrides). Document the mandatory "super-first" pattern explicitly in GODOT-DYNAMIC-THEME-RESEARCH.md as a load-bearing rule for Phase 4 implementation.
- **D-11 (Strict pass gate):** Feasibility only passes if **all** load-bearing checks pass: export-driven regeneration, subclass super-first overrides, runtime application, serialization behavior, and platform detection. A "mostly works" result is not enough to lock the architecture for Phase 4.
- **D-12 (Escalation rule):** If any strict-pass check fails, Phase 3.2 documents the failed check and escalates to the user before any fallback or workaround is locked. The research may analyze workarounds, but it must not quietly downgrade the architecture.
- **D-13 (Fallback recommendation):** If strict feasibility fails, Phase 3.2 must document fallback options and recommend the strongest fallback for user approval. Do not auto-fallback. Candidate fallback families include a hybrid `@tool` generator that produces static `.tres` files from the formula model, or the older 4N static `.tres` generator approach if runtime dynamism is not viable.

### Subclass Freedom (interactive refinement 2026-05-06)

- **D-17:** Subclasses follow a **hook-first hybrid** model. Named personality hooks/parameters are preferred for color formulas, radii, outline widths, and shape language. Direct theme-entry overrides are allowed only as documented exceptions after `super._regenerate()`.
- **D-18:** A coverage verifier is required as a design concept for Phase 4 and should be prototyped in Phase 3.2 if feasible. It checks that every required entry from the Phase 1 coverage matrix exists after each subclass regenerates.
- **D-19:** Subclasses may override mobile- or accessibility-sensitive values only when automated verification proves tap targets and contrast still pass. No subclass gets a free pass to shrink below mobile floors or violate WCAG contrast.
- **D-20:** `GODOT-DYNAMIC-THEME-RESEARCH.md` must include a **subclass contract table**: hook names/roles, allowed direct override categories, required verifier coverage, and forbidden APIs. This table is the bridge between creative subclass freedom and structural coverage guarantees.

### AUTO Platform Behavior (interactive refinement 2026-05-06)

- **D-21:** `platform=AUTO` uses a mobile-preferred fallback when detection is ambiguous, especially for Web/mobile-browser cases. The bias is intentional: oversize mobile UI on desktop is less dangerous than undersized desktop UI on touch devices.
- **D-22:** Phase 3.2 should research a **layered Godot-only detection strategy first**: `OS.has_feature("mobile")`, then `OS.get_name()` / platform-name behavior for native and Web targets, then mobile-preferred fallback if ambiguity remains. A JavaScript bridge is not part of the initial plan; research it only if the Godot-only path proves insufficient.
- **D-23:** `DESKTOP` and `MOBILE` remain explicit forced modes and are the documented escape hatch when AUTO detection is wrong.
- **D-24:** AUTO validation is **local plus simulated** in Phase 3.2: prove local desktop behavior and include an expected-output table or script for native desktop, native mobile, Web desktop, and Web mobile. The full export/device matrix remains Phase 10.

## Specific Ideas

- **The user's exact architecture intent (verbatim from 2026-05-04):**
  > "i need each theme to have a superclass that can dynamically handle via exports: flat/raised boolean, desktop/mobile boolean (for element and text sizes), base color & accent color (dynamically). the superclass would be called NeoCadeTheme and then the subclasses would prefix it with the type of theme it is."
  > "my hope is the superclass and universally handle flat/raised, desktop/mobile, and base/accent colors. and the subclasses would be focused entirely on the tints of the colors as well as the shapes and outlines."

- **Feasibility concern (verbatim):**
  > "there must be heavily research and if my idea is even possible implementation wise. im not sure if its possible to have the subclass dynamically change colors, raised, and sizes while leaving full creativity to the [sub]class themes for styles"

  This is the PRIMARY deliverable of Phase 3.2 — **prove feasibility with a working code spike** before further design work proceeds.

- **passivestar's `_get_base_color` formula** is the porting model — Phase 1 captured it verbatim. The formula is parameterized by `(brightness_offset, saturation_multiplier)`, which subclasses can tune for personality (e.g., higher saturation_multiplier for Prize Pop Plaza candy theme, lower for Cabinet Chrome professional theme).
- **`platform: AUTO` auto-detection** means a single `prize_pop_plaza_neocade_theme.tres` ships and the consumer doesn't need to pick a desktop vs mobile preset — the theme detects at runtime. This requires `OS.has_feature("mobile")` to be reliable across Godot 4.6's 6 export targets.
- **One `.tres` per theme is the v1 plan** (per user choice). v1 file count: N approved themes × 1 = N `.tres` files (was 4N under the old plan). Each subclass `.tres` saves ONLY the export values, not the regenerated entries.

## Deferred Ideas

- **Light theme variant** — exports could include a `dark: bool` toggle to invert the surface ramp; deferred to v2 unless feasibility spike trivially supports it.
- **Custom user palettes** — consumer overrides `base_color` / `accent_color` at runtime → theme regenerates. This is implicit in the architecture; no extra work needed.
- **Per-Control regeneration optimization** — if regenerating ALL theme entries on every export change is slow, Phase 3.2 may document an incremental-regen pattern (only regen what changed). Likely not needed; theme application is rare.
- **Multi-theme switching at runtime** (e.g., user picks a theme in-game) — the architecture supports this trivially; specific switching code is Phase 9 showcase concern.
