# Cross-AI Plan Review — Phase 3.1 Plans 01–06

## 1. Summary

The six plans form a well-structured research pipeline for Phase 3.1: skeleton creation → parallel MD3 and Flat-3D research → parallel MD3 Expressive synthesis and raised-matrix authoring → SOURCES.md closeout + cross-doc audit. The dependency graph (01→02|04→03|05→06) is sound, the hard-filter discipline is consistently enforced, and every plan explicitly prohibits `.tres`/`.gd`/font/icon/addon/mockup changes. The primary weakness is that all plans rely heavily on **web-fetching JS-rendered pages** (m3.material.io, itch.io, Google blog) without concrete fallback strategies — this was flagged in the Phase 3.1 RESEARCH.md but is not adequately planned for. Overall risk: **MEDIUM**.

## 2. Strengths

- **Dependency graph is correct.** Wave 0 (plan 01) produces skeletons → Wave 1 (plans 02 + 04) run in parallel on independent files → Wave 2 (plans 03 + 05) build on Wave 1 outputs → Wave 3 (plan 06) synthesizes everything. No circular deps.
- **Hard-filter discipline is pervasive.** Every plan embeds the anti-texture/anti-cyberpunk/anti-gradient/anti-soft-shadow filter in its must_haves, tasks, and verification. Phase 3.1 cannot drift back into the painterly territory Phase 3 was redirected from.
- **Extruded-flat `shadow_size=-1` conflict is identified early.** Plan 05 Task 1 explicitly calls out that the `shadow_size=-1` project rule (no soft shadows) may conflict with `shadow_offset` for extruded-flat and requires a fallback evaluation (recipe A vs recipe B). This is the right place to resolve this architectural tension.
- **Escape hatch TYPEVAR conflict is surfaced, not silently resolved.** Plan 05 Task 3 notes that `FlatButton` already exists in TYPEVAR-01 while `RaisedButton` does not, and mandates "must not edit REQUIREMENTS.md" — exactly the correct discipline for a research phase.
- **Composed mappings cover Godot-specific Controls.** Plan 02 correctly distinguishes exact MD3→Godot mappings, composed mappings (SpinBox, CodeEdit), and NeoCade-owned decisions (Tree, GraphEdit, etc.) — prevents forcing fake Material equivalents.
- **SOURCES.md integration follows the existing dossier pattern.** Plan 06 explicitly references the adopt/reject/open synthesis format used in Sections 1–10 of SOURCES.md.

## 4. Suggestions

- **S1 (for C1):** Add a source-access fallback clause to Plans 02, 03, and 04. If a JS-rendered URL returns insufficient content, the executor should: (1) try the raw GitHub token source equivalent (e.g., `material-components/material-web/tokens/versions`), (2) cite the specific file path and version pinned, (3) if neither works, mark the source row as "browser-verified required — capturing from training data with explicit caveat" and flag it for Phase 3.3/3.4 human review.
- **S2 (for C2):** Add a "Source Discovery Guidance" block to Plan 04 Task 2 with 3–4 seed platforms (itch.io tag "flat-ui", Godot Asset Library "GUI", commercial mobile games with known flat UI like "Monument Valley" or "Alto's Adventure") and a time-box of 2–3 attempts per platform.
- **S3 (for C3):** For Plans 02 and 03, add at least one verification step that checks a numeric value against a known authoritative source. Example: "Verify state-layer hover opacity by grepping the material-web token source for `hover-state-layer-opacity` and confirming the value in MD3-RESEARCH.md matches the upstream SCSS." This would partially address the hollow-verification concern.
- **S4 (for C4):** Add evaluation criteria to Plan 05 Task 1: (a) check `StyleBoxFlat.shadow_size` Godot 4.6 docs for whether `shadow_size=0` with `shadow_offset>0` renders a hard-edged offset shape (the desired extruded-flat behavior), (b) test in a throwaway Godot scene if needed, (c) if both fail, default to the two-stylebox composition recipe. This gives the executor a decision tree.
- **S5 (for C5):** Add a secondary source for MD3 Expressive to Plan 03: the Android Developers Compose Material 3 Expressive guide (`developer.android.com/develop/ui/compose/designsystems/material3-expressive`) as a fallback if the m3.material.io blog is unfetchable.
- **S6 (for C6):** In Plan 05 Task 2, add a "Where evidence is absent" note stating that families without public extruded-flat examples should be marked "NeoCade-owned decision" with rationale derived from MD3 principles, not fabricated citations.
- **S7 (for C7):** Consider splitting Plan 02 Task 1 into "Task 1a: Color + Type + Shape" and "Task 1b: State Layers + Elevation + Motion" to reduce blast radius of a partial failure.

## 5. Risk Assessment

**Overall: MEDIUM**

The plans are structurally sound and correctly bounded (pure research, no implementation). The MEDIUM rating is driven by two HIGH-severity concerns: (1) the absence of concrete fallback strategies for JS-rendered source pages that are the **core evidence sources** for the entire phase (m3.material.io, itch.io, Google blog), and (2) verification commands that test string presence rather than factual accuracy, which matters for a research phase whose primary deliverable is **accurate, citation-grade evidence**. If the JS-rendered pages are unfetchable and the fallback is training data with caveats, the evidence quality drops from "citation-grade" to "plausible," which weakens downstream Phase 3.3 direction derivation and Phase 3.4 mockup authority. The plan structure, dependency graph, and hard-filter enforcement are otherwise strong — no plans would silently mutate requirements or drift into implementation territory.
