<domain>
## Phase Boundary

Produce evidence-grade research on **Material Design 3**, **MD3 Expressive**, and **Flat-3D Game UI / Extruded Flat UI** patterns so Phase 3.3 can derive five flat-MD3 theme directions and Phase 3.4 can mock them up in both flat and raised variations.

This phase is visual-language research only. It does not create mockups, commit `.tres` styling, validate the dynamic `NeoCadeTheme` architecture, or implement Godot code. Architecture feasibility and code spikes belong to Phase 3.2; implementation belongs to Phase 4+.

**In scope:**
- Broad visual survey of official MD3/MD3 Expressive docs, Google design material, commercial mobile game UI, asset packs, design articles, and the user's itch.io references.
- MD3 foundations: color system, tonal palettes, semantic roles, type scale, shape scale, state layers, elevation principles, and component patterns.
- MD3 Expressive deltas: what becomes more playful, saturated, expressive, or shape-rich compared with baseline MD3.
- Flat-3D / extruded-flat pattern catalogue: solid-color top shape plus offset darker duplicate underneath, with no blur, gradient, texture, embossing, or painterly chrome.
- A flat-vs-raised Control-family matrix that says which Godot Control families should visually change between `raised=false` and `raised=true`.
- Concrete Godot visual recipe sketches: `StyleBoxFlat` construction notes, state-layer values, and Material component to Godot Control mappings.
- Anti-cyberpunk, anti-texture, anti-pixel-art filter audit for every adoption.
- `.planning/research/MD3-RESEARCH.md`, `.planning/research/FLAT-3D-UI-RESEARCH.md`, and `.planning/research/SOURCES.md` Sections 11 and 12 updates.

**Out of scope:**
- Deriving the five theme directions. Phase 3.3 owns that.
- Mockup creation or image generation. Phase 3.4 owns that.
- Validating `NeoCadeTheme` superclass/subclass architecture. Phase 3.2 owns that.
- Any `.tres`, `.gd`, font, icon, or addon layout commits.
- Choosing which N themes ship in v1.
- Re-rendering Phase 3 v0 concepts through the flat-MD3 filter.

<decisions>
## Implementation Decisions

### Research Source Bar

- **D-01:** Phase 3.1 uses a **broad visual survey**, not a narrow official-only source set. Official Material docs and Google sources are primary for MD3/MD3 Expressive facts, but asset packs, commercial mobile games, design articles, and UI screenshots are valid evidence for real-world flat/extruded game UI conventions.
- **D-02:** Every adoption from the broad survey must pass the hard filter:
  - **NO:** textures, patterns, embossing, painterly chrome, gradients on chrome, cyberpunk, synthwave/noir drift, or pixel art.
  - **YES:** flat MD3 + MD3 Expressive, colorful/playful/expressive, optional extruded-flat raised treatment using solid shape plus offset darker shape, no blur, no gradient.
- **D-03:** Inter Variable Roman remains the only v1 font assumption. Phase 3.1 must not adopt or recommend a separate display font, pixel font, mono font, or external font family as part of the theme.
- **D-04:** Sources should be labeled by evidence role: official/spec, upstream token source, user exemplar, commercial example, asset-pack example, or design commentary. Broad sources are allowed, but the research must distinguish authority from inspiration.

### Flat vs Raised Rules

- **D-05:** `raised` is primarily a **theme-wide toggle**:
  - `raised=false` means the flat baseline.
  - `raised=true` means broadly raised within Control groups where it improves affordance and still reads modern.
- **D-06:** Phase 3.1 must produce a **Control-family matrix** that specifies which Controls visually change between flat and raised modes. Starting intent:
  - Buttons and button-like controls change most visibly.
  - Panels mostly stay flat.
  - Popups/dialogs selectively gain raised treatment.
  - Inputs stay flat/outlined.
  - Labels, separators, and other non-interactive text/decorative slots do not change.
- **D-07:** Phase 3.1 must document per-Control escape hatches as type-variation concepts: `RaisedButton` for opt-in raised styling while `raised=false`, and `FlatButton` for opt-out flat styling while `raised=true`. If this expands or conflicts with the existing TYPEVAR list, the planner must surface it explicitly rather than silently changing requirements.
- **D-08:** Raised is **extruded-flat only**, not conventional 3D. The valid pattern is a solid top shape with an offset darker duplicate/shadow shape. No soft shadows, no blurred drop shadows, no bevel gradients, no texture, no engraving.

### v0 Direction DNA

- **D-09:** Phase 3.1 treats redirected Phase 3 concepts as **light DNA only**. It may mention loved/rejected traits as constraints for interpreting research, but it does not organize research around the old directions and does not derive new directions.
- **D-10:** Carry-forward DNA for interpretation:
  - Loved: Midnight Marquee and Cabinet Chrome dark, saturated colors.
  - Loved: Prize Pop Plaza childish-friendly tone and raised mobile-game feel.
  - Loved: Orbital Playdeck modern dark restraint and large rounded controls.
  - Hard reject: Boardwalk Sunset.
- **D-11:** Phase 3.3 owns the actual direction derivation. Phase 3.1 should provide vocabulary, source evidence, and filter rules that Phase 3.3 can use.

### Godot Translation Depth

- **D-12:** Phase 3.1 includes **concrete visual recipes**, not implementation code. Required translation outputs include:
  - `StyleBoxFlat` recipe sketches for flat and extruded-flat variants.
  - State-layer values and how they translate to Godot theme states.
  - Material component to Godot Control mapping table.
  - Notes on which mappings are exact, composed, or NeoCade-owned.
- **D-13:** The research should get specific enough that Phase 3.2 and Phase 4 know what visual formulas need support, but it must not validate architecture, write scripts, or decide code structure.
- **D-14:** For Godot-additive or non-Material controls, document composed mappings instead of forcing fake Material equivalents. Examples: `SpinBox` as text field plus stepper buttons, `CodeEdit` as text field plus gutter, `GraphEdit`/`GraphNode` as NeoCade-owned advanced surfaces.

### Output Structure

- **D-15:** Produce three research outputs:
  1. `.planning/research/MD3-RESEARCH.md` - MD3 + MD3 Expressive foundations, deltas, component patterns, state/elevation/type/shape/color details, anti-filter audit, and Godot mapping notes.
  2. `.planning/research/FLAT-3D-UI-RESEARCH.md` - flat/extruded game UI pattern catalogue, broad visual survey, user exemplar analysis, recipes, Control-family matrix, and anti-filter audit.
  3. `.planning/research/SOURCES.md` Sections 11 and 12 - adopt/reject/open synthesis following the existing dossier pattern.
- **D-16:** Both research docs should end with a "Flat vs Raised: When to Use Which" matrix. This matrix is advisory for downstream design, but the `raised` toggle semantics from D-05 through D-08 are locked unless later user approval changes them.

### the agent's Discretion

- Exact section ordering inside `MD3-RESEARCH.md` and `FLAT-3D-UI-RESEARCH.md`.
- Exact commercial/game UI examples beyond the user's two itch.io references, provided they are citation-grade and pass the hard filter.
- Whether to include side-by-side MD3 vs MD3 Expressive comparison tables.
- Whether glossary material appears near the top or in appendices.

</decisions>
