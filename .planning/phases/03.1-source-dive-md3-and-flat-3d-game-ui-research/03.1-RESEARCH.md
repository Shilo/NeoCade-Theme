# Phase 3.1 Planning Research - MD3, MD3 Expressive, and Flat-3D Game UI

**Researched:** 2026-05-05
**Purpose:** Planning support for Phase 3.1. This is not the final MD3 or Flat-3D research deliverable; it identifies the source map, artifact split, execution order, and verification risks needed to plan the source-dive well.

## Source Map for Planning

### Official/spec sources

- Material Design 3 official docs at `https://m3.material.io/` remain the canonical source for the public MD3 system. The site is JavaScript-rendered in this runtime, so execution plans must capture page URLs and use source screenshots/manual browser review if text extraction is incomplete.
- Material color system URL required by CONTEXT.md: `https://m3.material.io/styles/color/system/overview`.
- Material type scale token URL required by CONTEXT.md: `https://m3.material.io/styles/typography/type-scale-tokens`.
- Material shape scale token URL required by CONTEXT.md: `https://m3.material.io/styles/shape/shape-scale-tokens`.
- Material state layer URL required by CONTEXT.md: `https://m3.material.io/foundations/interaction/states/state-layers`.
- Material Web is the best accessible upstream token implementation for concrete token names and component-token mapping: `https://github.com/material-components/material-web`, especially `tokens/versions`, docs under `material-web.dev/theming/`, and component docs.
- Android Developers' Compose Material 3 guide is a useful corroborating source for concrete type scale values and component concepts: `https://developer.android.com/develop/ui/compose/designsystems/material3`.
- Godot official docs are canonical for visual recipe feasibility: `Theme`, `StyleBoxFlat`, and theme type variations at `https://docs.godotengine.org/en/stable/`.

### MD3 Expressive sources

- Google announced Material 3 Expressive publicly on 2025-05-13 in the Android/Wear OS refresh post: `https://blog.google/products-and-platforms/platforms/android/material-3-expressive-android-wearos-launch/`.
- Official Material site entry point for building with M3 Expressive: `https://m3.material.io/blog/building-with-m3-expressive`. This page is also JavaScript-rendered in this runtime, so the executor should verify it by browser/manual capture if needed.
- The Google post describes the evolution as more personal, fluid, glanceable, colorful, responsive, and typography-forward. For NeoCade, motion/haptics/blur are informational only or rejected because v1 is a static Godot Theme and the redirect forbids soft depth effects.

### User exemplars and broad inspiration sources

- User primary exemplar: `https://hcgamestudios.itch.io/flat-game-ui-for-mobile-games`. The page explicitly describes a casual, colorful, flat mobile GUI pack; lists many mobile UI surfaces; and emphasizes editable vector shapes and PNG output.
- User secondary exemplar: `https://fajrulaslim.itch.io/ui-button-flat-design/devlog/157464/ui-button-flat-design`. The page describes vector Illustrator/EPS sources plus PNG sprites for many flat button/icon models.
- Broad sources are valid only as inspiration, never authority. Plans must label evidence role: official/spec, upstream token source, user exemplar, commercial example, asset-pack example, or design commentary.

## Planning Implications

Phase 3.1 should produce three final artifacts during execution:

1. `.planning/research/MD3-RESEARCH.md`
2. `.planning/research/FLAT-3D-UI-RESEARCH.md`
3. `.planning/research/SOURCES.md` Sections 11 and 12

The work naturally separates into two research lanes:

- MD3 lane: source acquisition, MD3 foundation extraction, Godot mapping, then MD3 Expressive synthesis.
- Flat-3D lane: source acquisition, pattern catalogue, Godot recipe sketches, then flat-vs-raised Control-family matrix.

`SOURCES.md` should be last because it depends on the final adopt/reject/open synthesis from both lanes.

## Specific Risks to Plan Around

- JS-rendered Material docs can defeat plain text scraping. Executor plans need browser/manual capture fallbacks and should cite URLs plus captured facts rather than relying only on `curl` or training memory.
- MD3 Expressive includes motion, blur, haptics, and Android/Wear OS platform features. NeoCade v1 can adopt only the static visual vocabulary: color, scale, shape, emphasis, and glanceable hierarchy.
- Flat-3D/extruded game UI examples often use PNG sprites, gradients, bevels, or texture-like highlights. The Phase 3.1 hard filter accepts only the solid top shape plus offset darker duplicate pattern.
- `RaisedButton` and `FlatButton` escape hatches may conflict with the existing TYPEVAR list, where `FlatButton` already exists and `RaisedButton` does not. Plans should surface this as a research note, not mutate requirements.
- The flat-vs-raised matrix must use the existing Control coverage axis from FEATURES.md and MINIMAL-THEME-COVERAGE-DELTA.md; do not invent a new Control taxonomy.
- This phase must not edit `.tres`, `.gd`, font, icon, or addon files.

## Recommended Plan Split

1. Provenance and artifact skeletons.
2. MD3 foundations and Godot mapping.
3. MD3 Expressive synthesis.
4. Flat-3D source survey and pattern catalogue.
5. Flat-vs-raised matrix and StyleBoxFlat recipes.
6. SOURCES.md sections plus final cross-document audit.
