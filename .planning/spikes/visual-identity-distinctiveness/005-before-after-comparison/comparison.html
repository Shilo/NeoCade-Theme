The practical question: do regular controls look unique?

The original goal was to escape "feels like a generic Godot Editor theme with a tint." Phase 12 + 13 land most of their visual delta on type variations (PrimaryButton, DangerButton, Kicker, SuccessLabel, AccentPanel, etc.) and selected states (selected tab top stripe, selected ItemList/Tree row left stripe). The base Button / CheckBox / OptionButton / MenuButton / LinkButton classes — the ones a consumer drops into a scene without any setup — are visually nearly identical before vs after.

This is by design: the locked SC#6 invariant forbids new exports, and the spike series chose "redistribute existing accent into idle chrome" (C2') and "type variations as opt-in" (Phase 13) over auto-binding role colors to defaults. But it leaves the user-facing complaint partially open. The table below is the honest accounting per control class.

Bottom line: most of the "more unique" delivery requires the consumer to either (a) reach for a type variation (theme_type_variation = &"PrimaryButton") or (b) build UI that uses selected-state chrome (tabs, lists, trees). A scene that just drops Button + CheckBox + OptionButton still reads as "generic Godot with a tint" for those controls. If you want the default Button class to render distinctively per direction without opt-in, that's a separate scope: it would either require auto-binding role colors to default Button states (rejected by user 2026-05-10 — accessibility concern) or applying per-direction shape signatures to the default Button recipe (a future Phase 14+ candidate). Phase 12 + 13 chose the conservative path.

If you want regular controls to look more unique without opt-in

Phase 12 + 13 were scoped to ship inside the locked 12-export / SC#3-default-chrome-unchanged contract. A future Phase 14: Default Chrome Identity could close this gap if you want. Concrete candidates (each maintains SC#1-#6 invariants):

  • Default Button per-direction tinting: apply each direction's accent_subtle as a faint left-border or inner-shadow on the default Button class so a plain Button reads as "this is a Bubble button" vs "this is a Burst button" without opt-in. No new hues — uses existing tokens.
  • Per-direction Button corner radius: right now default Button uses shape.secondary_radius which is similar across directions. Bind it to a direction-specific shape.button_radius so Bubble's default Button is round, Pulse's is sharp, Slate's is rounded, etc.
  • Per-direction CheckBox/Radio icon: the tick mark and radio dot could pick up Burst's "celebration spark" vs Daybreak's "soft check" — but this requires SVG asset changes (new scope).
  • OptionButton arrow icon: different per-direction arrow glyphs (chevron sharp for Pulse, soft curve for Daybreak, etc.) — also requires SVG asset changes.
  • Apply C6 shape signatures to MORE recipes: currently Burst's primary_min_height only fires on .primary_strategy recipes. Could extend to apply scaled-down version to default Button (e.g., +8px height on Burst, +0 on Slate) so default Buttons look bigger in Burst without needing PrimaryButton variation.

These are real follow-up candidates if "the default Button still looks generic" is a ship-blocker. None of them violate the locked invariants; they're just NEW shape keys that didn't make Phase 12's scope.
